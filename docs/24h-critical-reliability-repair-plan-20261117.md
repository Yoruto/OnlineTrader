# OnlineTrader 24 小时持续运行重大问题修复与验收计划

> 编写日期：2026-11-17  
> 审查基线（main）：`9d561172f95d1a8ee5b00de341004199f948bc60`  
> 状态：**待实施、待独立验收**。本文是开发实施规格，不代表代码修复或 24 小时实测已经完成。  
> 适用范围：`Yoruto/OnlineTrader`，区分桌面旧 Kernel 执行链和 `dsv replacement-run` / `simnow replacement-run` 替代候选链。

## 1. 目标、范围和放行原则

目标是保证在至少连续 24 小时（含夜盘、休市、跨自然日、开市恢复）运行中，**不出现重复发送、无凭据推定撤单、错误持仓归属、保护责任丢失、已恢复却永久停开、快照失联导致无控制通道，以及数据与日志积累导致实时线程失去响应**。24 小时是最小可靠性基线，不能代替跨柜台交易日的独立验证。

本次修复计划优先处理上一轮已确认问题，并与用户已在并行修复的两项工作集成：A. Windows 不可信墙钟 / 应用参考 UTC；B. Tick 增量批次和会话重建的计算成本。A、B 不由本计划重复改写实现，只规定接口、阻断门槛与验收对接条件。

**绝对约束：** 一个账户一个订单 owner / 一个 SQLite writer；行情历史重放不能补发旧信号；`UNKNOWN` 继续占用风险与待处理量；柜台已明确拒单与发出后未知不是同一状态；重试必须有新尝试身份及事实前提；不能通过清空账本、重启、手工改终态、增大行情年龄容差或关闭保护掩盖问题。保留原 DSV 正常业务语义，新增异常恢复差异需记录原因、前后状态及批准范围。

## 3. 修复设计：阶段性工程任务

### PR-01 / R01：授时暂停与撤单派发解耦（P0）

**根因：** STOP 同步触发撤单的时机处于 adapter dispatch-disabled 阶段，导致“确定没有调用 SDK”的本地拒绝被作为可能执行过的未知结果。

**建议实施：**
1. 为授时暂停新增语义明确的 `PAUSE_ENTRIES_FOR_CLOCK` 或内部等价操作，只做停开、保留当前订单/仓位及登记待撤责任；不在 `enabled=False` 的准备阶段调用 SDK。
2. 在 owner 已完成原生事实核对、已准备效果持久化、适配器进入可派发状态后，按原控制器执行已归属订单的撤单。人工 STOP 与授时暂停需要共享安全撤单底层，但保留不同的恢复授权语义。
3. 明确区分 `PRE_SEND_NOT_ATTEMPTED`、`CALL_RETURNED`、`UNKNOWN_AFTER_CALL`；仅当代码能证明尚未进入 SDK 取消方法时可将本地派发错误登记为“未尝试”，不能改变已发/未知订单的占量事实。
4. 不得简单给整个 `step()` 提前设置 `enabled=True`，以免错误开放发送窗口；保留 SDK owner 线程、账号、日历、交易日及提交先于派发校验。
5. 增加持仓非零、部分成交、正在撤单、断线同时授时失败的竞态测试。

**验收：** 虚拟授时失效且在途 OPEN 时，新增开仓为 0；明确有权限可取消的订单恰好调用一次 SDK 撤单；本地预派发失败绝不伪装为柜台 UNKNOWN；恢复后没有重复 SEND。

### PR-02 / R02：参考时间冲突后的可信锚点重建（P0/P1）

**根因：** 新样本与旧锚点差值超过 250ms 时只拒绝刷新，没有独立可信参考的重新收敛/接受路径；最大 900 秒保护保持会到期。

**建议实施：**
1. 定义状态：`CALIBRATED`、`REFERENCE_PENDING`、`REFERENCE_CONFLICT`、`RECALIBRATING`、`HOLDOVER_PROTECTION`、`REFERENCE_EXPIRED`。不同状态显式规定开仓、撤单、已有持仓保护、观察和恢复权限。
2. 连续至少两次、跨合理间隔、来自独立可信来源且离散度符合配置的样本可作为“新参考候选”；需验证 RTT/来源/跨日/跃变幅度和拒绝重放。**不能仅因为同一源连续报告同一错误时间就接受。**
3. 建立新锚点时如需较大校正，先进入恢复核对；禁止使用突然改写的 UTC 跳过或倒退重放日历事件。新参考可信 ≠ 自动重新开仓。
4. `_timestamp` 的缓慢校正不能无限积累，记录已应用和剩余校正量、最大预计收敛时间、时钟 epoch；保存锚点只能在已验证状态，持久化失败不得声称恢复有保证。
5. 900 秒/1 秒误差预算作为当前工程边界保留。预算到期后仍要持续接收、去重及核对柜台事实；无法证明绝对 UTC 时明确显示“退出责任已登记、执行时间依据不足”，禁止假报已平仓。
6. 设计 24 小时无网络时的降级操作方案（风险提示、人工介入/柜台原有止损机制），不能声称 NTP 断网 24 小时仍具有完整自动保护。

**验收：** 注入旧锚点与至少两个可信新源相差 ±0.3、±0.4、±1、±5 秒；冲突时不自动开仓，参考重新收敛后可达可核对的 DISARMED 状态；在有仓、无仓、UNKNOWN 三种状态分别测试恢复。

### PR-03 / R03：统一报价年龄与自动续开门禁（P1）

1. 新增或复用一个带 `raw_signed_age_ns`、`estimated_error_ns`、`quality`、`session_id`、`source_epoch` 的结构；在 SDK 原始报价处仅规范化，不篡改纳秒源身份。
2. 普通策略年龄配置 0 的 DSV 语义保持不变；**自动恢复权限的工程门禁**若更严格（例如 5 秒）须独立命名、记录原因，不能假称它是原 DSV 规则。
3. 决策、临发单、授时恢复使用同一时间质量解释，允许误差范围内的小幅负年龄而拒绝明显未来、跨盘、乱序及过期快照。不要以 `abs(age)` 或 `max(age,0)` 无条件绕过检查。
4. 测试 −250ms、−100ms、−50ms、0、+50ms、+5s 及边界外样本；同时验证多合约单个异常不会改变其他合约报价年龄。

**验收：** 质量层 VALID 的误差内领先样本不因恢复层零下限被再次拒绝；错误时间仍不能获得新风险授权。

### PR-04 / R04-R05：工作台快照有界发布和可靠控制（P1）

1. `read_workbench_publication()` 校验 `0 <= monotonic_now - published_ns < MAX_AGE_NS`；若过期，返回不可用并走可控回退路径。
2. 发布端在生成**合并后**的 `base + view + protocol` 时进行字节预算；历史 cycle/order/trade 使用分页或独立只读明细投影，当前自有持仓、在途订单、异常块及账户标识永不被无说明截断。
3. 发布失败记录 `PUBLICATION_OVERSIZE` / `PUBLICATION_FAILED` 与最近成功更新时间，旧帧仅作为明确标记的历史显示；不能伪装为最新。
4. IPC fallback 使用 owner 支持的权威快照/命令通道，严格限时与优先级。不能因 UI 状态过期永久屏蔽合法 STOP/CANCEL/REDUCE 请求；但操作必须由 owner 重新核对身份与柜台事实，不允许直接用旧 UI 数据盲发。
5. 历史分页限制在只读视图，禁止修改底层持仓/成交保留记录。保持 1MiB 协议上界或以版本化协议兼容升级，不能只“把帧调大”。

**验收：** 构造 0、100、2,000、10,000 历史周期及超大单周期，强制发布失败、断开快照 pipe、GUI 重连；工作台 5 秒后不得持续接纳旧帧为新；可获得明确错误，权威操作路径可用且不可重复发单。Qt/Windows IPC 单独实测。

### PR-05 / R06-R07：拒单、拒撤、未知结果的受控恢复（P1）

1. 独立列出状态矩阵：`REJECTED` 订单终态、`CANCELLED` 终态、`DEFINITELY_NOT_SENT`、`CALL_RETURNED`、`UNKNOWN`、`ALIVE`、部分成交、迟到成交、旧交易日今昨仓。
2. `REDUCE` 已明确 `REJECTED` 且没有未确认残量时，增加“重新核对后启动新的退出尝试”操作：校验原生持仓归属、活动单、已成交数量、今昨仓路由、交易时间与合法报价；明确新子单 ID 和原订单因果关系。
3. 前一次 `UNKNOWN` 不允许以用户重复点击建立第二 SEND/CANCEL。先通过原生订单/成交和柜台终态事实核对，保持原占量及异常可见性。
4. `cancel_status` 不再兼任“已经尝试过”“结果未知”“已确认”全部含义。引入按子单递增的 `cancel_attempt_id` 与尝试明细；只有已核实的明确失败或已确定未调用才可建立新的取消尝试。
5. 已确认成交部分应先核对，再按剩余目标与路由开立新单；不以旧委托名义修改原价/数量，不重复计算成交。人工恢复入口应明确操作结果（可执行、需核对、条件不足），不能只接收目标后静默不动作。
6. 旧 Kernel 的既有“拒单不自动无限重报”回归必须保留，新增恢复流程需独立批准后才启用；替代链和旧链分别验收。

**验收：** 明确拒单 → 新核对 → 再减仓；拒撤 → 新尝试；撤单 UNKNOWN → 迟到成交 → 归属更新；跨日 SHFE/INE 今昨仓。全程不出现超量、重复发送、虚构终态。

### PR-06 / R08：持久化事实去重与长时数据预算（P2）

1. 对 ORDER 使用身份、终态/累计成交量/原生版本生成事实指纹；未变化的快照不重复写 `NATIVE_ORDER` 事件和 `native_orders` 行。保持迟到成交和终态纠正可检测，不盲目忽略已终态订单的新事实。
2. 将审计“每轮 heartbeat”与状态变化事件分层；若保留每轮 ROUND，需设置明确磁盘预算、轮次输入大小、归档和只读恢复索引策略。
3. 确认 WAL checkpoint、磁盘剩余空间、同步写入耗时与启动恢复耗时。不能删除当前执行责任、订单身份、成交、UNKNOWN 和必要财务事实。
4. 如需压缩/归档，只在受控冷态或不破坏单 writer 的专用流程实施，并有版本化回放验证；先做变更去重，后决定是否需要归档。
5. 日志滚动与 SQLite WAL 维护需计入 24 小时存储预算，不允许磁盘写失败后继续发单。

**验收：** 100 终态订单 × 1,000 未变化轮次，新增 ORDER 写入应近于状态变更次数而非 100,000；注入一笔迟到成交仍被准确接纳。采用至少三档历史规模做 CPU、RSS、WAL、事件行数、事务 p95/p99 对照。

### PR-07 / R09-R10：与时钟、Tick 两项并行修复集成（阻断项）

1. Tick feed 使用增量游标+边界重叠校验；重建路径按可恢复小批次执行，但不得改变原始分钟消费或在回放阶段开新仓。与另一分支接口对齐，不能覆盖其在研代码。
2. 形成统一 `sdk_observed_mono`、`batch_started/finished_mono`、`rebuild_started/finished_mono`、`strategy_started/finished_mono`、`pre_dispatch_mono` 的可追踪链路。
3. **发单前重新取参考时间及真实 SDK 报价身份**，不得沿用长任务开始前缓存时间；在途订单/已有持仓管理优先于重建结果发布。
4. 对 5 秒重建耗时、持续流量超过处理能力、10 分钟静默及单合约乱序分别故障注入，严格区分“上游实际延迟”“本机处理积压”“时钟证据不足”。
5. 集成在固定 SHA 上进行；使用 PR 先合并无冲突接口，再合并实质重构。保留“最新已验证提交”的测试记录，避免测试某一 SHA 后直接声称后续提交已通过。

| ID | 故障注入 | 必须断言 |

| T01 | 授时失效，空仓无委托 | 禁新增，行情/账本仍可观察，无虚假 UNKNOWN |
| T02 | 授时失效，有 ALIVE 开仓单且 cancel_on_stop=true | 撤单一次进入合法 SDK owner，保留在途占量 |

| T05 | SDK cancel 调用中异常 | 记录 UNKNOWN，禁止盲重发 |
| T06 | 撤单被柜台明确拒绝 | 经核对后产生新 cancel attempt，使用独立 ID |
| T07 | 迟到 CANCELLED/TRADE 交错 | 只计算一次真实成交，不出现负持仓 |
| T08 | 平仓单 REJECTED | 旧单终态保持，新核对后可受控重新退出 |
| T09 | 平仓单 UNKNOWN | 不形成重复退出委托 |
| T10 | SHFE/INE 跨日今昨仓 | 路由及归属正确；不误平他人仓 |
| T11 | NTP 参考候选持续相差 400ms | 可进入重校准核对，不永久锁旧锚点 |
| T12 | NTP 参考候选跳 5s 且来源不一致 | 不自动接受跳变，不开仓 |
| T13 | NTP 失联 1/5/15/30 分钟 | 保持期精确，超期仍能观察柜台责任但不假报可执行 |
| T14 | 系统墙钟向前/后跳 5 秒 | 不污染应用参考单调差值与行情年龄 |
| T15 | 负年龄 −50ms，误差为 100ms | 质量一致；允许在其他门禁满足时恢复 |
| T16 | 真实未来报价 / 跨盘报价 | 拒绝、可观测，不引入其他合约误判 |
| T17 | 旧快照已超过 5 秒 | 只展示历史或回退权威查询，不接受为新快照 |
| T18 | 快照序列化超过 1MiB | 有界退化，不能永久阻断合法控制 |
| T19 | 2,000/10,000 历史周期 | 启动、刷新内存/CPU/IPC 容量有证据 |
| T20 | 100 个终态订单 × 1,000 无变化轮次 | 不重复生成 100,000 条 NATIVE_ORDER |
| T21 | 终态订单后出现新的逐笔成交事实 | 接纳并核对修正，不因去重漏掉 |
| T22 | 5 秒 Tick 路径重建 | 不执行旧信号、柜台处理有机会推进、发单时校验实际年龄 |
| T23 | 休市、夜盘、跨自然日 | 不误判断流；已有退出责任不消失 |
| T24 | 授时恢复后人工 STOP/重启/换日 | 不擅自自动续开 |
| T25 | 单合约异常、其他合约正常 | 不以异常时间戳推进全账户日切 |
| T26 | SQL 写入异常、WAL 达到阈值 | 不先发单后悄悄丢失必须持久化事实 |
| T27 | 连续 24 小时运行含至少一次持仓退出 | 每个关键阶段有可复核事件链 |
| T28 | 控制端退出、GUI 关闭重开 | 原 owner 责任不因 GUI 生命周期消失 |

所有门槛必须覆盖小于、等于、大于的边界；配置阈值来源应在测试结果中明确，不能把示例参数当成生产默认。固定 DSV 冻结原件的顺序和双端真实发送回放要单独列入策略一致性验收。

## 6. 24 小时运行与资源预算

### 6.1 运行场景

使用**实际 Windows 目标机器/打包运行入口**，在授权的 SimNow 或隔离模拟环境运行完整交易周期。推荐一个基线运行 + 一个故障注入运行，不能把两次短跑拼成同一个连续 24 小时。必须覆盖夜盘、休市、日盘开盘、已有订单的终态核对，以及至少一次真实模拟柜台的开平闭环；如果自然没有信号，应记为 NOT_RUN，另通过可复核回放覆盖，但不能说真实开平已 PASS。

启动前保留历史订单、成交及已关闭周期，运行中提供部分成交、明确拒单和撤单结果变更的 QA 场景。采集 SDK 原始报价时间、app UTC、系统 UTC、单调锚点、来源 epoch、订单与成交身份、各环节耗时、GC/RSS/CPU、数据库/WAL及日志体积。

### 6.2 量化指标与阻断方式

下列阈值是**建议的初始工程验收预算**，不是交易所、DSV 或 Windows 的已证事实；应按真实硬件测量基线后冻结为版本参数：

| 指标 | 初始建议 | 阻断条件 |
| --- | --- | --- |
| SDK 泵调用间隔 p99 | ≤ 1 秒（正常流量） | 若持续超过，诊断并不放行长时 |
| 单次业务阶段最大耗时 | 正常 ≤ 1 秒；故障重建应分片 | 大于 5 秒且不能让出 owner |
| 策略事件到发单前检查 | 无未记录的处理时间 | 发生 5 秒处理而仍使用旧时间样本 |
| 关键状态快照新鲜度 | 正常不超过 5 秒 | 旧帧持续冒充最新或无法进行受控操作 |
| 内存、事件行数、WAL 与日志大小 | 24 小时曲线可解释、无持续无界斜率 | 不变订单每轮重复写库或超容量后不可恢复 |
| 时钟误差/保持 | 使用来源和误差区间的明确定义 | 未证时间被当成“可信”，或可信重校准无恢复出口 |
| 业务正确性 | 零重复 SEND、零重复成交记账、零虚构 CANCELLED | 任何一项发生即 FAIL |

每 60 秒输出聚合诊断，异常时保留前后原始窗口。文件、交易数据与账户信息应脱敏，且禁止将真实凭据上传到 GitHub。磁盘告警不能自动删除在途责任、交易事实或未知结果。

### 6.3 24 小时 PASS 的定义

- 运行进程连续且未发生未经批准的 owner 切换；但进程存活只是必要不充分条件。
- 当日/夜盘交易日历、授权及真实柜台日范围有证据；有限授权到期后不误开仓，原持仓和在途责任仍继续核对。
- 每笔开仓、撤单、成交、减仓和退出均可从提交事件关联到 SDK 原生身份；资金/风险占量始终守恒。
- 注入网络、授时、快照和存储异常后，系统进入明确状态，条件满足时存在受控恢复出口，无需清库或重启绕过。
- 有持仓期间不能因为 GUI 关闭、快照发布失败、授时刷新失败而静默丢失保护责任；如果无法合法派单，必须显示具体阻断和人工处置条件。
- 所有 FAIL/NOT_RUN 如实列出。真实柜台未验证不能用离线 PASS 冒充；原版 DSV 不具备的异常行为应登记工程差异。

## 7. 回滚、部署与升级

- 每批修改使用独立可撤销 PR，任何活跃发送者必须在有完整柜台终态、归属与数据库兼容性证明后才能替换。
- 涉及 Journal/订单尝试 schema 的 PR 需要设计最低 writer 版本、冷备份、兼容读路径和拒绝旧写入者；不得让旧程序静默忽略新状态继续发送。
- 更新安装器只在所有已知账户排他锁可取得且原订单持仓已核清后执行；程序内“暂停开仓”≠ 空仓且安全更新。
- 运行中有 UNKNOWN、ALIVE、未终态减仓单或未解除的保护责任时：先恢复旧 owner 核对，不允许为了上线新补丁强制杀进程。
- 回滚不能反向解释未知的新版状态；计划发布时注明单独“只读恢复旧账本”策略。
