## 1. 产品目标与确定边界

OnlineTrader 对用户表现为一款普通 Windows 期货交易软件：解压发行包、双击 `OnlineTrader.exe`，Runtime 自动读取发行配置或用户有效配置、准备行情与模拟柜台，工作台使用原有视觉布局；用户用现有“开始策略”“停止策略”按钮控制 DSV。窗口 X 默认最小化至托盘，托盘退出整个软件须通过 Runtime 安全退出门禁。

架构为**单台电脑默认使用一个账号、一套本地 Runtime 和一个交易策略会话**；用户可能在 A、B 不同电脑、不同时间使用同一个模拟账号，甚至使用不同策略。**不设计跨电脑策略同步、控制权仲裁、主备接管或 SQLite 文件互拷**。两台电脑各保留自己的 Config、本地策略执行账本和 Tick 缓存；跨电脑共享的只是柜台或数据服务能回查的**账户层历史事实**，在各自本地 SQLite 后台补齐。

交付包默认携带测试模拟账号及策略配置；默认测试账号可以反复使用和入金，**不要求旧账本 handoff、首次使用向导或用户历史包**。仍必须核对启动时当前柜台持仓与活动委托；本地新账本不得把外部持仓认作本策略自有持仓。

明确不在本期开发：UI 换肤/布局重排、初始化向导、云服务、跨机数据库双向同步、跨机策略恢复、分布式 Owner Lease/Fencing、多策略管理平台、Redis/Kafka/PostgreSQL Server、全量 Tick 历史平台、重写 DSV 核心规则。

## 2. 总体模块和权威关系

```text
OnlineTrader.exe
    |
Desktop Bootstrap  -- (attach/start) --> Trading Runtime (唯一 SDK/交易决策 Owner)
    |                                    |-- Configuration (desired / effective)
Existing Workbench <--- IPC views --------|-- Strategy + OMS + Risk + Gateway
    |                                    |-- SQLite Ledger (每账户唯一 writer)
    |                                    |-- Account History Sync (有界后台读/写任务)
    |                                    |-- Market Cache (内存优先，短期磁盘可选)
    +-- original buttons/tray ---------->|-- Recovery / Reconciliation
```

关键边界：

- Config 表达**用户希望怎样运行**；原账本保存**发生过的事实、已生效配置版本、未决命令和恢复证据**；当前原生订单/成交/持仓以柜台观察为外部事实，经 Runtime 验证并持久化。
- Qt 不直接调用交易 SDK、不写交易账本、不改变业务终态；Runtime 每次命令须进行账号、boot、配置版本和风险验证。
- 单账户一个执行 Owner、一个账本 Writer；历史、报表和行情缓存可被降级/限速，不得造成关键交易提交积压。
- 同一个 SQLite 可以包含“本机执行事实”与“柜台全账户历史观察”，但必须在字段、来源和服务接口上区分，不允许把 B 电脑同步来的订单归为 A 电脑的 DSV 自有订单。

## 3. 配置发行、用户修改与升级保护

### 3.1 配置分层

发行包内有 Default Config，用于部署测试模拟账号、初始合约、策略参数和 Runtime 控制开关。用户使用后形成 User Config，包含他实际保存的账号、合约、策略参数、定时配置和软件偏好。Runtime 根据**有效配置**运作，实际交易参数版本必须沿用现有 Ledger `config_revisions`、Profile Hash、`authority.config_revision`。

用户目录和发行默认目录应逻辑隔离；实现时优先兼容既有便携 `runtime/`、`runtime.json`、`OnlineTrader-parameters.json`、`runtime-control.json`、`private/OnlineTrader-defaults.json` 与 `PortableAccountStore`，不强制一次性更名搬迁。

示例目标逻辑结构（**非迁移指令**）：

```text
OnlineTrader/
  OnlineTrader.exe
  OnlineTraderCLI.exe
  _internal/
  defaults/                      # 可由升级覆盖的发行默认模板
  runtime/                       # 持久用户数据目录，更新时保留
    runtime.json
    runtime-control.json
    OnlineTrader-parameters.json
    private/OnlineTrader-defaults.json
    data/<account>/ledger.db
    market_cache/
    logs/
```

### 3.2 加载与初始化规则

1. 当前用户有效配置存在且合法：直接加载，不以新版 defaults 覆盖账号、合约或策略参数。
2. 用户配置不存在：将发行默认配置初始化为用户配置，严格保留私有资料的权限与日志脱敏要求；**无初始化向导**。
3. 默认模拟账号第一次没有本地账本：在通过账户身份与现有初始化/排他条件后允许创建本地账本；不要因为模拟账号可能已有柜台历史就要求旧电脑 handoff。
4. 用户已经使用过的本地账本存在：严格以原身份校验、原 schema 和原恢复合同打开，不能新建空库掩盖已存在账本丢失、WAL 或损坏。
5. 发行 defaults 更新时，可以为新字段提供**兼容且明确的迁移默认值**，但不能把用户手动删除的合约重新加回来，也不能替换用户有效参数。
6. 用户配置 Schema 无法兼容时 fail-closed 并保留原文件，不通过恢复出厂值消除错误。

不要对不同版本 JSON 进行不受控深度合并；账号切换需先核对旧账号已有交易保护责任。账号秘密不能进入公开同步日志或 PR 证据。

### 3.3 配置修改和生效

| 操作 | 用户配置归属 | 生效合同 |
| --- | --- | --- |
| 增加/移除合约 | User Config | 校验合约，策略运行中按原 DSV 生效时机；不能移除未履行保护责任 |
| 修改参数 | User Config + 现有 Ledger config revision | Runtime 预览，事务成功后再改变内存有效 Profile |
| 切换账号 | User Config | 核对旧账号交易责任，再关闭旧 Owner/附着或启动新 Owner |
| 定时启动总开关 | `runtime-control.json` | 继续使用现有“只阻止新的自动启动，不停止已有 owner”语义 |
| 窗口大小、托盘偏好 | Client UI Preferences | 本地立即生效，不进入交易账本 |

Config 分为 Default、Saved User、Runtime Effective 三种语义。现有 `config_revisions` 与有效 Profile 的恢复逻辑已经具备核心能力，本期**不另造 CONFIG_APPLIED 平行事件体系**。

### 3.4 更新流程

更新器必须保留完整用户数据目录、原账本和其 WAL 状态；程序文件与用户数据分开处理。新程序启动时校验 Application / Config Schema / Ledger Schema / IPC Protocol / Strategy Rule 版本，必要时做显式可验证迁移，失败保留旧数据并可回退，不能自动清空用户参数、账号、历史或持仓状态。Runtime 正承担持仓/订单责任时升级也必须经过现有安全约束，不因界面关闭而强杀 owner。

## 4. SQLite 长期事实模型

每账户沿用原执行 `ledger.db`，原 Schema 有效部分优先复用，不新增第二个 Runtime 交易数据库，不允许历史同步模块成为并行 writer。

| 逻辑类别 | 内容 | 生命周期 |
| --- | --- | --- |
| 本地执行事实 | 发单意图、OMS effect、回执、UNKNOWN、策略周期与保护 | 长期；严格恢复语义 |
| Native 账户观察 | 全账户历史原生报单、成交、持仓观察、可取得的资金快照 | 长期；带来源、日期、覆盖率 |
| Effective Config | `config_revisions` / authority / 配置哈希 | 长期；复用原实现 |
| 审计事件 | 用户控制、重连、关键诊断和恢复结果 | 长期、必要信息脱敏 |
| Sync Metadata | 账户/日期/类别的数据源、水位、状态、尝试、错误 | 可增量维护 |
| 程序调试日志 | IPC 重试、Worker 延迟、性能统计 | 轮转文本，不无限塞入交易 Ledger |

继续使用现有单 Writer、WAL 和持久化事务合同；保留发送前 durability。不允许通过删除 `-wal`、`-shm`、猜测数据或重复发送未知命令修复数据异常。

对“本机执行事实”和“远端账户历史”必须明确区分：**同步来的账户原生订单只能加入账户观察数据；不得反向创建本机 DSV 策略 ownership 或重置保护规则**。

## 5. 账户历史自动补齐（Account History Sync）

### 5.1 用户可见目标

例：A 电脑运行两天策略 A，B 电脑运行两天策略 B，回到 A 电脑后：
- 继续使用 A 自己的策略与参数；
- Runtime 优先恢复当前交易/行情；
- 后台从柜台或合规历史服务读取 B 运行期间可查的账户订单、成交、资金历史；
- 写入 A 本地原账本的“账户观察”部分并刷新权益/报单/成交历史显示；
- 回到 B 时按同一机制从可用数据源补齐 A 后续历史；
- **两电脑不互相访问 SQLite，也不互相同步策略**。

可用性边界：普通 CTP/TqSdk/SimNow 历史查询可能只返回有限日期及有限字段。必须逐数据源确认可回查日期、跨日游标、资金字段及完整性证明。无法查到的历史显示“缺失或不可用”，不能宣称全账户历史完整。

### 5.2 两层同步优先级

**P0 必要当前事实（交易动作的前置门禁）：**账号身份、当前持仓、当前活动订单、相关成交、UNKNOWN 与恢复责任、柜台同步覆盖率。没有达到对应可信条件不得恢复相关不安全动作。

**P1 后台历史（不阻塞策略）：**历史订单、历史成交、逐日账户资金与权益、可取得的历史持仓、图表更新和统计。可分页、限速、断点重试，不应拖慢 SDK pump、策略轮次、关键 Ledger commit。

### 5.3 最小 Sync 元数据合同（字段建议）

```text
(account_key, source, trading_day, category)
status: NOT_REQUESTED | SYNCING | PARTIAL | COMPLETE | UNAVAILABLE | FAILED
cursor / coverage_from / coverage_to
last_attempt_at / last_success_at
source_revision_or_snapshot_id (如可提供)
last_error_code
```

`COMPLETE` 只能用于数据源对目标范围提供可证实完整覆盖的情况；返回空列表不自动证明历史完整。对失败或部分缺失日期按下次可用时重试，不能把无历史错误吞掉或补造。

### 5.4 去重与一致性

- 以交易日、账户、交易所/柜台订单或成交业务标识建立稳定唯一键，具体依据 SDK/交易所实际 ID 唯一性语义；不以合约+时间+价格判重。
- 使用事务化 UPSERT / UNIQUE 约束；同标识异内容要产生结构化冲突诊断，不可静默覆盖。
- 每次同步写入记录来源和外部身份，并与本地 execution ownership 分开。
- 重复运行同步结果幂等；网络中断后从已确认的覆盖水位补齐。
- 历史量较大时按账户、日期、类别分页；Worker 有界排队、限速和可取消，写入经原账本 Writer 串行化；不允许历史长事务抢占关键执行确认。
- 同步结果和导入/持久化动作均可审计；不把 SDK 异常堆栈或凭据展示到普通 GUI。

### 5.5 盈利与权益曲线

默认为**整个交易账户的权益曲线**，而不是 A/B 电脑单个策略的收益。账户权益、入金出金、平仓盈亏、浮动盈亏、手续费是不同事实；不可将权益变化全部叫交易利润。优先根据已取得的可信逐日资金快照绘图；缺失交易日必须留缺口/覆盖提示，不能用插值冒充真实盈亏。

## 6. Tick 缓存

本期只关注当日和最近约 3 个**期货交易日**行情；优先当前内存 latest tick / 有界 Ring Buffer，不增加时间序列数据库。建议以每合约数量/内存上限限制占用；行情解码及展示数据可适度 coalesce，但**策略消费和交易风险判定不得因 UI 节流丢失必要事件**。

磁盘缓存为后续可选功能，只有确实需要跨重启查看最近 3 日 Tick 时再评估按交易日+合约写 Parquet/其他分片文件。夜盘按柜台交易日分组，不按普通自然日午夜切分；过期交易日删除前确保不影响正在消费的只读查询。Cache I/O 失败不阻断交易 Owner。Tick Cache 绝不是完整可恢复交易证据；止损、保护、实际下单决策需要的持久化事实仍归原 Ledger。

## 7. 启动顺序与后台调度

```text
双击 EXE
  → Desktop Bootstrap 附着/启动 DISARMED Runtime
  → Config + 原 Ledger 校验和恢复
  → Gateway 行情/柜台连接、时间和交易日验证
  → 当前订单/成交/持仓 + UNKNOWN/保护责任核对
  → 原策略运行条件/授权判断（含 300 秒恢复窗口）
  → Workbench 展示真实 Runtime 状态
  → 后台有界 Account History Sync / 曲线 / 报表 / Cache 清理
```

注意启动步骤可合理并发，但所有 P0 依赖必须满足，不能用“后台同步慢慢做”拖延关键当前订单和持仓核对。新版 Runtime 不得因长期图表、收益曲线、大帧编码或历史查询阻塞交易 owner。历史下载的网络/CPU/数据库预算与行情 SDK pump 和订单提交分别监控。

推荐阶段和用户反馈：配置/原账本读取、行情连接、柜台同步、恢复核对、策略就绪、历史同步中。沿用原工作台已有状态/消息区域，不新增主界面和视觉布局。

## 8. 单机 300 秒自动恢复

### 8.1 用户意图优先

用户曾明确点击“开始策略”，且当前实际有效授权允许交易；发生**非用户主动**的网络/SDK/Runtime 短时中断时，系统可以自动重连，重新获取柜台事实并对账。

- 以失去最后可信运行状态时刻为 T0，**必须在 T0 + 300 秒以内完成连接和必要核对**才能继承之前的自动开仓授权。
- 300 秒内可信恢复：可自动继续 DSV 正常策略交易（包括后续合规开仓、平仓、撤单），不需要再点击按钮。
- 超过 300 秒：恢复已有订单/保护责任，新增开仓保持关闭，等待用户点击原有“开始策略”。
- 用户主动 STOP/PAUSE/禁开，不因为断线重连自动撤销。
- 缺少可靠中断时间、原有效授权、配置/账户身份、账本完整性、柜台对账、时钟可信性时，不自动继承开仓授权。
- 不补发断线期间错过的历史信号、不自动重发 UNKNOWN；按 DSV 现有 freshness/交易时段/风控规则继续决策。

对于同一进程可用单调时钟计时；跨 boot/Windows 重启要依赖经检查的持久时间证据，无法证明 300 秒以内则 fail-closed。超过窗口不等于解除已有持仓保护，原止盈/止损的恢复责任仍应履行。

这项恢复功能必须**复用现有** Kernel、Ledger、gateway、Reconciliation，不能并行造第二套策略规则。

## 9. 原界面下的操作生命周期

| 操作 | 预期行为 |
| --- | --- |
| 双击发行 EXE | 启动/附着 Runtime，显示**现有 Workbench** |
| 重复双击 | 单实例窗口恢复/前置，不能重复启动 Owner |
| 原“开始策略”按钮（及既有 F5） | 经过 Runtime 真正校验后开始/授权策略 |
| 原“停止策略” | 停止新增开仓，已有保护责任按原合同履行 |
| 点击窗口 X | 默认隐藏到托盘，运行策略和 Runtime 均继续 |
| 托盘显示/双击图标 | 恢复原窗口，不触发策略命令 |
| 托盘退出整个 OnlineTrader | Runtime 先审核交易责任，再完成优雅停机，最后关闭 Qt |

**安全退出门禁**：有本账户持仓、活动委托、UNKNOWN/SEND_POSSIBLE、保护责任、账本/柜台状态无法证明或恢复未完成时，正常托盘退出被拒绝；通过现有 Qt 原生弹窗解释原因并留在托盘/工作台。普通用户不提供“强制杀交易进程”按钮。

允许退出时停止新增请求、等待已受理命令明确结论、完成必要账本提交、关闭 Gateway/SDK、释放 Writer/账户锁、关闭 View、验证对应 Runtime 进程真实终止，再关闭 Qt。没有停机完成证据不能宣称退出成功。Windows 强制关机、停电和 Task Manager kill 无法由此保证优雅终止，必须交给恢复路径。

实施时参考独立桌面生命周期方案；不在此文档 PR 中修改 UI，也不暗中实现新的进程终止路径。

## 10. 新电脑首次使用（无向导）

发行包带默认模拟账户及策略 Config。新电脑双击：若用户配置不存在则初始化；若本地账本不存在且符合默认模拟账号首次初始化条件则创建；连接柜台、查询当前状态、展示原有 Workbench，用户点击开始策略。**不要求默认测试账号的旧电脑账本交接**，不需要查询另一电脑的本地 SQLite 文件。

如果以后用户在另一台电脑使用相同账户，不同步策略，只由 Account History Sync 在可用数据范围内补齐其委托、成交、资金和权益。保持每台电脑有效配置和本地 DSV 持仓责任独立。

## 11. 实施计划、拆分与验收

| 阶段 | 主要任务 | 源码级验收 |
| --- | --- | --- |
| P1 Config/Update | 默认/用户 Config 逻辑隔离、初始化与版本迁移、用户参数/账号/合约不被覆盖 | 新目录可加载默认配置；用户修改后升级保留原 effective Profile 和数据库 |
| P2 Boot/Priority | 标注 P0/P1，保留现有 Runtime 主体；历史后台任务不得阻塞交易 Owner | 当前状态核对优先、性能可观测，GUI 保持原布局 |
| P3 Account History Sync | 数据源能力审计、按天覆盖、分页/重试/去重/资金及曲线 | A/B 不同策略仍可补账户历史；重复同步幂等；无法获取历史明确 PARTIAL/UNAVAILABLE |
| P4 Recovery 300s | 中断时间、权限持续性、重连+reconcile、超时人工开始 | ≤300s 可信恢复续跑；>300s 不自动新增；主动停止不被撤销 |
| P5 UX Shutdown | 重复双击唤醒、X 托盘、安全退出全受控进程 | 有仓/未知禁止正常退出；空仓且无订单完成受控退出 |
| P6 Tick（可选） | 内存有界缓存、必要时三交易日磁盘分片 | 缓存不影响 SDK pump，磁盘故障可降级 |

建议 PR 分批且依赖清晰：配置/升级、账户历史数据源审计、后台同步、恢复时窗、桌面生命周期、Tick Cache。不要把 Schema 迁移、交易策略修改和大规模 UI 拆分一起塞进同一 PR。

### 测试矩阵

- Config：首次初始化、修改/删除合约、参数修订、新版本新增字段、用户账号保留、损坏配置与不可逆迁移拒绝。
- Ledger：新建/已有账户、Writer/锁/WAL、原订单/UNKNOWN 恢复、并发历史只读、重复同步与 ID 冲突。
- 历史：跨日分页、上游只提供部分历史、空结果不假 COMPLETE、失败重试、资金曲线入金出金区分、A/B 不同策略记录不改变本机自有仓。
- Runtime：当前行情/柜台优先，历史大任务时 Owner pump/写 ACK 的 P50/P95/P99 可观察。
- Recovery：断线 30/299/301 秒、恢复恰在 300 秒边界、跨 boot 时间不可证、人工 STOP、UNKNOWN、持仓保护状态连续。
- UX：Windows 可见 GUI、重复启动、窗口 X/托盘、危险状态禁止退出、无风险全进程退出、Runtime 退出失败准确反馈。
- Delivery：配置便携 ZIP/EXE，旧用户升级、参数和原账本数据不被替换，干净机器启动；**需另获打包授权**。

源码 Unit/Integration/Windows GUI、SimNow 登录或自动交易测试均按各次任务授权执行。报告记录完整 `git_sha`、配置摘要（脱敏）、环境、测试集、PASS/FAIL/SKIP/NOT_RUN、运行日志、SQLite/包版本；不得把已有旧候选测试作为本次新功能验收。

## 12. 最终不可破坏的不变量

1. 界面外观、布局、导航、控件位置保持不变。
2. 默认测试账号可直接使用；没有额外初始化向导。
3. 更新程序不静默覆盖用户账号、合约、参数、原账本和私有设置。
4. Config 管目标配置，Ledger 管已发生和已生效事实，Tick Cache 管短期非权威行情。
5. 一个本机账户一个交易 owner/writer；不改变 DSV 策略既有业务规则。
6. 当前交易事实和保护优先于全部历史同步和收益图表。
7. A/B 电脑可使用同账号不同策略；只补齐可获得的账户历史，不同步策略。
8. 未知、缺失或无法证明完整的历史数据不得伪装完整。
9. 用户主动停止不被自动重连解除；300 秒可信恢复允许自动续跑，超时需重新点击开始。
10. 普通 X 仅隐藏到托盘；正常退出需 Runtime 核对并验证全部相关受控进程退出。
11. Tick 暂时内存优先；三交易日磁盘缓存可选，不变成订单恢复权威。
12. 不一次性重写 Kernel、替换现有 Config Revision、删除 WAL/SHM 或自行开展未授权交易测试/打包。

**目标用户体验**：用户只需关注账号、合约、参数和开始/停止；软件自动读取配置、优先保证行情与策略、后台补齐账户历史、短时故障自动恢复，且更新不丢用户数据。
