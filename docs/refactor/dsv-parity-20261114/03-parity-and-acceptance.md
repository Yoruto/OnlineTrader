# 03｜DSV一致性、故障与发布验收规范

返回 [总览](README.md)。下列84项是**待实施的用例族**，每族还需参数化；不是已执行84项测试，也不是承诺仅84项足够。初始执行状态全部为NOT_RUN。业务预期未从原版证明的，标为EXPECTATION_PENDING，不用OnlineTrader自身结果填充。

## 1. 验收对象

比较对象为冻结DSV发行包及其实际配置/SDK，与候选重构版本。旧OnlineTrader用于识别回归与迁移影响，不是业务真值。原版成熟性是选择基准的理由，不是“所有异常均已正确”的测试结论。

需要比较：每轮实际可见输入、决策时点、方向、理论价、目标手数、首报及后续报价、开平标志、任务撤改、机会消费、统计状态、保护阶段、停开原因及恢复结果。真实成交受外部环境影响，不能要求两个独立账户产生相同成交价后才算业务一致，也不能因最终盈亏接近就认为过程一致。

## 2. 证据层级

| 层级 | 证据 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| L0 | 固定源码/字节码/随包SDK控制流 | 分支和静态来源 | 真实网络下的时序 |
| L1 | 原纯函数或独立语义片段，同输入运行 | 该片段输出和边界 | 整个应用行为 |
| L2 | 候选完整运行器+注入原生事实，并与原版可执行/独立证据比较 | 业务与执行链组合 | 真实柜台接入和Windows安装 |
| L3 | Windows原生Qt/IPC/安装制品测试 | UI、生命周期、打包和权限 | 真实报单可成交 |
| L4 | 明确授权的在线模拟/原版对跑 | 原生接入及所覆盖真实路径 | 未出现过的所有市场条件 |

用L1模型验证一个缺陷，不得写成L4实测。仅源码检查通过不等于功能通过。原版输出只能来自独立来源；候选实现不能同时充当比较器的预期生成器。

## 3. 黄金样本格式

每个样本必须有以下内容，建议按JSONL事件及一个manifest保存：

```text
case_id / fixture_revision / rule_ids / evidence_level
reference_exe_sha256 / reference_sdk_version / sdk_file_hashes
candidate_commit / runtime_version / environment_manifest
source_business_config / interpreted_config / application_boundary
initial_business_state / initial_native_state
ordered_events（包含每轮wait_update分组、用户命令、时钟读数）
expected_decisions / expected_state_changes / expected_execution_actions
native_id_mapping / expected_logs（按语义，不要求文字排版相同）
assertions / unsupported_dimensions / redaction_policy / fixture_sha256
```

价格保留原始数值表示与tick单位；原生时间保留原精度，额外UTC表示注明转换方式。NaN、None、零和缺字段不能在录制时混为一类。多合约更新顺序和资金共享状态不能被排序器悄悄重排。

录制样本里出现的个人信息、token、密码、完整真实账号、报表私有内容不入Git。通过稳定匿名映射保持身份关系；不得把脱敏后的两个不同原生ID合并。

## 4. 比较器原则

### 4.1 三层比较

第一层：纯业务输出及状态。第二层：控制器请求/SDK任务行为和子单动作。第三层：原生回报后的订单、数量和业务统计。发现第一处分歧立即保留输入及前状态，再继续分析，不用后续假成交掩盖。

随机生成订单ID可建立双射映射，但不能忽略方向、开平、价格、数量、目标版本和先后关系。只有来源证明不影响业务的字段允许规范化。原版日志整秒而候选纳秒，不强行认定顺序相同或不同。

当候选根本没有创建对应订单时，不能继续将参考成交硬灌给候选以得到相同最终仓位。执行用例采用受控外部事实脚本，并在逻辑订单映射失败时报告分歧。在线双账户结果则分别报告输入差异、执行差异和柜台成交差异。

### 4.2 合理的变形测试

可以改变日志可写性、GUI刷新/连接状态、报表是否打开、比较器是否启动，验证业务轨迹不变。可以重复相同原生成交，验证不重复计数。不能无证把价格整体平移或交易日整体平移后要求所有输出不变：限价比例、到期、时段及日历可能改变。

### 4.3 测试结果状态

`PASS / FAIL / BLOCKED / NOT_RUN / EXPECTATION_PENDING / NOT_APPLICABLE / APPROVED_DEVIATION`。

NOT_APPLICABLE必须对应明确产品范围，不可用于遮盖原版支持而新软件未做的功能。APPROVED_DEVIATION附用户确认或ADR，不允许开发者自己把失败改名。

| C083 | U01 | 校时成功、无权限、无网、服务失败、调整后偏差 | 独立运维收据和复测，不在SDK线程执行，不引入未批准交易门禁 |
| C084 | L4对照 | 当前授权模拟账户、共同行情、自然及受控场景 | 实际目标、委托与原生事实对应；无信号区间不得算交易路径通过 |

## 12. 三个必须完整保留的反例样本

### 12.1 自定义撤单监督删除不是“撤单已成功”

初始有平仓单，发出撤单后只收到调用返回；30秒和60秒都无终态。预期来自原包普通等待：原单数量仍占用，不重报；额外诊断可以出现，但不以工程自拟阈值触发全局交易状态变化。随后补入迟到成交和终态，验证剩余量再推进。另开样本测试任务退出finally的30秒清理，不合并。

### 12.2 历史观察不能提前吃掉当前机会

历史片段出现超追价拒绝，当前实时回到触发价且其他原版条件允许。记录原版是否消费、何时消费；候选必须相同。特别检查候选分支、拒绝分支、延续分支和旧状态迁移。不能只断言最终订单数量为1，还要检查成交前目标和分钟状态。

### 12.3 日志成功恢复不等于运行已经结束

旧记录恢复到事件101，状态RECOVERED且无finalized；之后发生事件102，进程中断，独立索引不可用。迁移器根据可信原目录/账户/账本识别未结束，保留后续事实。展示日志是否补全与交易账户状态相互独立。

## 13. 日志最低字段

`observed_at`、`native_time`、`account_alias`、`contract`、`trading_day`、`run_id`、`input_id`、`decision_id`、`rule_ids`、`command_id/target_id`、原生订单/成交映射、动作阶段、拒绝原因、实际值与要求值、状态前后摘要、异常类型及脱敏栈、采集版本。

每个“触价不下单”都必须能回答：原版规则是否真的满足、是否仍处观察回补、是否已有目标、发送是否发生、回报是否回来。不能只给“策略复核失败”。不得为了日志列全原因重复执行有副作用的规则。
