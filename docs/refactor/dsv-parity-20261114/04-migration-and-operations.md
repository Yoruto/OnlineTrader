# 04｜迁移、冷切换、回滚与长期运行方案

返回 [总览](README.md)。本文件是实施流程，不是立即操作指令。本次未连接账户、修改数据库、安装软件、调整Windows时间或创建自动任务。

## 1. 四条迁移原则

1. 原版DSV安装、配置、凭据和账户数据保持原位；新产品只读取经授权的脱敏业务资料，不导入整个原环境。
2. 旧OnlineTrader账本只读保存。新核心使用新schema和新数据目录，不通过原地改表把旧周期伪装成新周期。
3. 第一次切核心采用冷切换：选定交易范围无持仓、无活动委托、无未核清发送/撤单/成交，旧控制者已退出后新控制者才可接管。
4. 空仓不等于业务状态为空。当天报单计数、分钟消费、止损冷却、日/月停止和夜盘参考可能仍影响下一次交易，必须保留或在被证明的自然重置边界转换。

冷切换是部署边界，不是永久新增的策略交易限制；它不意味着运行中出现仓位就停策略。若未来必须带仓热迁移，应另立项目和验收，不能在本计划中顺手实现。

## 2. 状态分类与迁移方式

| 状态 | 处置 | 核验 |
| --- | --- | --- |
| 账户凭据 | 保留现有凭据存储引用，必要时由用户重新绑定 | provider/账户一致；凭据值不入导出包 |
| 原始业务参数 | 复制经验证的业务字段 | 原保存值、零值、枚举和解释前后结果一致 |
| 已计算偏移及输入来源 | 保留原计算结果和原输入身份 | 不因升级重新算持仓/当日参数 |
| 日/月策略统计 | 版本化转换 | 次数、点数、止损次数、日停/月停、统计日一致 |
| 分钟机会与冷却 | 保留可证明的状态或选择合法重置边界 | 不把未知消费来源清成未用 |
| 夜盘参考与延续次数 | 独立转换 | 交易日、参考行情和已尝试状态准确 |
| 已关闭周期和成交历史 | 旧库只读归档，新视图可读取映射 | 原身份、数量、价格、费用不改写 |
| 活动周期/挂单/未知发送 | 不在首次冷切换中导入接管 | 仍由原控制者管理；未核清则中止迁移 |
| 旧授权/上下文/epoch | 不作为新交易许可导入 | 保留审计记录，不自动变为新运行授权 |
| 外部仓/外部订单 | 不自动采用 | 原版接管范围及用户指令未证时不扩大权限 |
| 中文日志 | 可只读归档或按事件重建 | 不作为成交真值，不触发交易 |
| 历史日志恢复回执 | 一次性迁移器处理 | 核对账户、boot、目录、原账本和事件水位 |
| QA与比较结果 | 保留证据索引 | 不作为正式运行状态或额度 |

任何转换都输出来源版本、字段映射、丢弃字段及理由。没有明确含义的字段留在归档，不猜测为零或false；影响当日交易的未知字段必须阻止发布切换而不是在运行时继续猜。

## 3. 新旧执行排他

沿用并验证与旧进程互通的账户级排他命名，不能新引擎另建一个不同锁名后自认为单实例。记录provider、稳定账户键、进程身份、控制器版本和会话ID，不包含口令。

切换时需要同时证明：旧进程不再驱动SDK、旧任务不会继续产生子单、旧账户没有未结状态、新进程尚无发送能力。仅GUI退出、仅锁文件删除、仅本地列表为空都不够。

影子运行只接收复制的事件/快照，不持有真实SDK订单对象和send/cancel句柄。SDK可能在wait_update中推进已创建任务，所以“我没显式调用insert_order”不构成只读证明。影子路径不能创建可执行TargetPosTask。

## 4. 冷切换M0–M9

| 步骤 | 操作与证据 | 失败/中止条件 |
| --- | --- | --- |
| M0 冻结发布材料 | 记录旧代码、新制品、SDK、规则清单、有效业务配置和部署范围 | 任何哈希不匹配或仍有未核交易差异 |
| M1 进入维护窗口 | 通过明确维护操作停止新增业务目标，保留原订单/仓位责任 | 不把F6、平仓、杀进程混用；未确认命令效果 |
| M2 核清选定范围 | 查原生持仓、活动单、终态、逐笔成交及未知结果，与旧账本一致 | 任一活动单/持仓/未知/成交缺口；不得为切换偷偷强平 |
| M3 生成一致备份 | 旧writer稳定后用一致性备份方式保存库及所需附属文件、业务配置和版本 | 不能只复制仍在变化的SQLite主文件忽略WAL |
| M4 只读转换预检 | 在副本上读取旧状态，输出字段级迁移差异及不可映射项 | 非零业务状态被清空、未知schema、错误账户 |
| M5 导入新状态 | 写新目录、新schema；提交迁移收据和来源水位，不覆盖旧库 | 中断或校验失败则丢弃未发布的新目录，源仍不变 |
| M6 对照恢复预览 | 新核心禁发送地评估相同输入，核对业务状态及下一动作 | 任一未解释差异，尤其是升级后突然允许新开仓 |
| M7 旧控制者退出 | 明确结束SDK任务/连接，记录旧进程退出并释放排他权 | 仍有旧任务、进程未知或退出清理未完 |
| M8 新控制者接管 | 新进程取得同一排他权，重新核对当前原生事实与迁移状态 | 维护期间外部交易导致事实变化，不能凭旧快照继续 |
| M9 用户恢复运行 | 使用当前明确启动操作；记录运行/观察状态和首次有效新输入 | 旧日志或定时器不得代替本次启动授权；启动语义需符合D14 |

M2和M8之间可能有外部活动，第二次核对不可省略。交易账户的外部操作无法由本地锁完全阻止；部署窗口应约定外部操作暂停，并仍验证实际柜台事实。

第一次切换可选择原版定义的交易日重置边界以减少转换复杂度，但必须证明该边界真实发生。不能把维护开始时间、午夜或重启时间当作交易日重置。

## 5. 迁移收据

拟议字段：`migration_id`、源应用/存储版本、源备份哈希、源业务状态水位、目标应用/存储版本、目标状态哈希、账户匿名绑定、原生核对摘要、规则版本、转换器版本、每字段转换结果、未迁移字段、操作者、时间、回滚材料位置。

收据只证明转换，不授予下单。重复执行相同转换应得到相同业务结果；不得重复追加成交。转换脚本默认dry-run，写入新目录需要显式选项，禁止默认覆盖已有目标库。

## 6. 回滚矩阵

| 情况 | 允许的回滚路径 | 禁止操作 |
| --- | --- | --- |
| 新版尚未接管/未发新指令 | 丢弃未发布目录，恢复旧制品与一致备份，重新核对后按原流程启动 | 新旧同时持有账户执行权 |
| 新版接管但没有新增订单/成交/业务消费 | 核验事实和业务水位确无变化，再切回旧控制者 | 仅看成交为0就断言状态未变化 |
| 新版已下单但全部核清、当前空仓 | 转换新版产生的订单/成交和当日业务状态，或者等待原版合法重置边界后按既定迁移方案回旧版 | 直接恢复升级前旧库，导致次数、日停和消费回退 |
| 新版仍有持仓或活动单 | 新控制者继续承担已接管责任；采用经过验收的故障处置，不做热切 | 杀掉新进程让旧引擎按旧账本接管 |
| 新版发送结果未知 | 保留原身份和潜在数量，先核对真实柜台 | 将异常当作未发送，再由旧版补单 |
| 反向转换尚未实现 | 不开放承诺式“一键回滚”；发布前必须给出可行安全窗口方案 | 把二进制可回退写成状态可回退 |

恢复旧版本本身不授予旧测试scope新的额度。回滚后的账户事实和业务规则仍需正确，不可重复使用已消费的一次性模拟许可。

## 7. 日志体系迁移

### 7.1 新运行路径

交易/命令/恢复事实保存在明确存储中，可读日志只作投影。正常日志追加、轮转和展示不维持另一套影响交易授权的状态机。历史重建在独立工具/后台只读任务中运行，无SDK控制权限。

### 7.2 旧格式处理

TRACKING表明曾登记，不证明尾部已写完；DEGRADED/REBUILDING表明需要核对；RECOVERED仅证明某一水位曾恢复。旧版缺少finalized字段时不视为已结束。只有明确且核验成立的结束记录才能跳过后续核对。

定位顺序：可信原账本登记 → 同账户原运行布局和身份文件 → 对应备用回执。备用JSON中的任意路径不能直接成为读取/写入目标。检查解析大小、路径规范化、目录归属、boot/账户绑定、符号链接及事件水位。转换输出写到新归档，不覆盖来源证据。

异常退出可能丢失某些临时诊断行，必须如实说明。关键成交/目标事实若未持久化不能用一条“日志已恢复”掩盖；要回到原生证据核查。

### 7.3 可以退役什么

新主循环中的旧索引扫描、旧回执版本分支、历史运行后台修复驱动可退役。原日志原文件、旧数据库、原版本取证记录保留只读，不删除审计历史。

## 8. 故障处置矩阵

下表是待实现并验收的职责要求，不保证当前代码已经如此。每个动作必须属于D、U或I，不能偷加X型交易规则。

| 故障 | 继续什么 | 限制什么 | 明确禁止 |
| --- | --- | --- | --- |
| GUI断开/崩溃 | 单交易进程继续已接受业务；用户可重新附着 | 暂无GUI新命令 | GUI finally关闭SDK |
| 中文日志失败 | 业务、SDK、关键事实继续 | 日志展示降级 | 因格式化失败全局停开 |
| 比较器/报表失败 | 正常策略与原订单管理 | 仅比较/导出 | 比较参数文件变化撤销交易权限 |
| 网络断开 | 保留原身份、目标和未知占用 | 按实际连接和原版流程处理新动作 | 把未收到回报当成订单不存在 |
| SDK已知拒单 | 原版错误分支和记录 | 对应任务/目标按原版 | 自动补一个新机会“补偿测试” |
| 撤单长时间无终态 | 原单占用、回报接收和原等待语义 | 可告警 | 时间流逝释放数量或重复重报 |
| 关键存储失败 | 仍能接收的原生事实和已接管责任按验收策略处理 | 未记录的新目标不交执行者 | 用内存成功冒充持久化成功 |
| SDK已有未完成目标且关键存储失效 | 必须按ADR08验证过的策略维持/收敛责任并告警 | 新目标与未接受操作 | 声称禁止新目标即可禁止SDK原目标全部剩余开仓 |
| 时钟偏差告警 | DSV实际业务路径；偏差状态可见 | U校时操作受维护规则管理 | 直接新增全局交易资格锁存 |
| 时钟跳变且输入不能解释 | 按已证原版行为/明确异常策略处理，暴露保护状态 | 不能制造有效报价或假交易日 | 只写“保护继续”却没有执行证据 |
| 原生事实冲突/未知发送 | 原身份、原数量和核对证据 | 对有歧义的对象不做重复风险动作 | 覆盖冲突或清库重启 |
| 磁盘/权限/系统故障 | 已证明可执行的应急责任与明确告警 | 受影响持久化/部署 | 为恢复界面而强杀唯一管理者 |

如果路线A无法在关键存储失败、用户停止等条件下明确控制已接受目标的后续子单，G1不得通过。不能将这个问题推迟到正式上线后再解决。

## 9. 7×24部署定义

7×24指应用可长期部署、被监控、按计划恢复连接与交易日生命周期，不等于SDK连接永远不重建。官方文档对跨日连接和未结任务有风险提示（E16），但不能据此每天固定时刻直接杀进程。

建议常驻桌面/监督层与账户交易进程分开。监督层只检查进程、心跳和明确退出原因；不持有下单凭据或策略对象来成为第二执行者。进程无响应时先告警、保存诊断和核查责任，不能在旧进程生死未知时启动另一sender。

受控轮换须满足：原交易日事实核齐、无未结订单和待处理持仓或已有经过验收的接管机制、业务日状态已保存、原连接明确退出。选择哪个窗口由原版行为、交易时段和实际状态决定，不由文档猜固定时间。

## 10. 自动校时U01独立交付

用户确实要求自动校准，不应永久以“只能检测”代替。实施可分层，但交付状态必须诚实：

1. 偏差检测：异步采样、来源/偏差/失败记录，不参与业务规则判定。
2. 维护窗口执行：核对系统权限与时间服务，执行经过明确授权的同步，读取结果并重新测量。
3. 对运行中的影响：测试前跳、后退、调整期间IPC/SDK更新、已有任务等待、日志顺序及收盘规则。
4. 有仓自动调整：未完成第3项及相应原版/用户差异处理前，不作为已支持能力。不得靠新增price_only等长期例外系统绕开未决问题。

同步失败不能假报“已校准”；服务启动成功不等于偏差已修正。校时记录包括前后偏差、来源、系统动作、退出码、权限结果、复测及当前业务阶段；不记录管理员凭据。

实现独立运维模块不意味着可以绕过当前会话的系统修改权限。此文档不执行任何同步命令。

## 11. 健康监控与资源边界

必要指标：SDK更新间隔、行情原生年龄、业务处理耗时、目标接受与原生回报延迟、待核订单数量、最长撤单等待、writer积压、视图队列、内存/线程/文件句柄、日志与库增长、当前账户控制者、业务停止原因。

指标阈值先用于诊断。任何阈值触发交易动作必须有D/U/I依据及测试，不通过“运维配置”绕过规则登记。UI“连接正常”不得代替“订单核清”；UI“保护中”必须对应当前执行路径与已验证输入，否则显示具体待恢复原因。

日志轮转只处理展示日志；原生事实保留和归档策略单独配置。磁盘容量需结合实际事件速率测量，不在计划里凭空给固定保留天数。大报表使用只读快照，不能占住交易writer。

## 12. 配置更新、热更新和升级

首版不做运行中替换交易核心。代码升级按冷切换；业务参数编辑、预览、保存和生效按原DSV语义分别实现。已有目标或保护的参数不能因热加载文件而改变。

界面文本、只读报表等非交易组件可独立更新，但IPC兼容性必须验证。任何影响目标计算、任务定价或状态解释的变更，都属于交易核心变更，不能以“修一个小bug”绕过回归和迁移。

未来带仓热更需证明订单身份、SDK任务生命周期、保护状态和单执行者交接，另立ADR。本次不为未来可能的热更保留复杂通用epoch/插件平台。

## 13. 历史审计项的结案方式

| 项目 | 正确结案方式 | 错误结案方式 |
| --- | --- | --- |
| 自定义30秒撤单监督冻结 | 若机制退役，记录其非DSV来源、删除闭包及原等待语义测试 | 修计时后直接称DSV一致 |
| 跳钟后保护问题 | 新正常路径/原版行为和用户附加需求各自验收 | 只验证特例函数返回True |
| 旧日志RECOVERED兼容 | 一次性迁移器覆盖缺字段与后续事件 | 忽略旧文件或全部当finalized |
| 日志恢复提示被遮蔽 | 新视图身份校验测试通过 | 只修改变量名不测共存场景 |
| 自动校时 | U01实际校准和复测证据 | 仅NTP检测成功 |
| 原版自身疑似缺陷 | 记录实际发行版行为；改进另列差异 | 暗中修掉后仍称零业务差异 |

## 14. 发布签署清单

发布前审核者逐项填结果与证据，不允许只写“通过”：固定版本；规则清单；原版功能目录；SDK选型；ADR08保证；唯一sender；关键数量与身份测试；配置与业务日状态；迁移/反向回滚；Windows制品；只读与在线模拟授权；原版对跑可比区间；长稳覆盖；自动校时状态；已知限制；部署责任人；当前账户事实；维护窗口；首次运行核查。

任何关键项为FAIL/EXPECTATION_PENDING/未覆盖，不能完成相应发布签署。阶段性离线交付允许保留在线NOT_RUN，但必须明确这不是正式交易验收。

## 15. 最终交接材料

交付：固定版源码与制品哈希、依赖锁、规则来源表、全部用例结果、支持范围、迁移工具及收据、旧版本只读归档、恢复手册、日志字段说明、校时流程、故障责任表、升级/回滚步骤及退役代码清单。

现场用户应能直接回答：当前是哪一个控制者；某次触价为什么未下单；哪个订单仍未终结；当日停止来自哪个原版规则；GUI关闭后谁负责持仓；新版本失败时如何不重复交易地回退。做不到这些，不应仅凭界面完成或测试数量宣布重构结束。
