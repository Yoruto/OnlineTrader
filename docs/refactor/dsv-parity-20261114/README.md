## 1. 最终要交付什么

保留有用的 Qt 界面、账户管理和基础设施，以冻结版本的 DSV 实际业务行为为依据，替换 OnlineTrader 中过度通用、重复决策及未经批准的增强机制。最终形成：**一个策略业务核心、一个执行控制者、一套可解释的状态、一条可追溯的事实记录链**。

用户要求的是“界面可以不同，逻辑必须一致”。因此，本项目不是重新设计一个“更合理”的交易策略，也不是通过删除校验让所有信号都下单。每个开仓、不开仓、撤单、改价、平仓及状态消费结果，都必须能够回到 DSV 证据或用户明确要求。

### 1.1 本计划的核心决策

| 决策 | 处理 |
| --- | --- |
| 重构范围 | 保留外围，替换交易核心；不继续在旧通用内核内永久堆叠兼容分支 |
| 规则来源 | DSV 已证行为、用户明确需求、最小执行事实约束、未证增强四类分别管理 |
| 自发增加的交易规则 | 默认进入删除候选，不以“现有测试要求如此”为保留依据 |
| SDK 执行 | QA 直接运行原版 TargetPosTask 和子单任务。候选采用保留逐单提交证据的显式执行控制器 |
| 最小正确性 | 保留单执行者、成交去重、未知结果不重放、未终态数量不释放、用户停止不被自动撤销 |
| 日志与比较 | 不参与策略决策；可读日志和对照报告从交易控制中分离 |
| 校时 | DSV 兼容行为与用户新增的自动校时需求分开；不借校时引入新的策略门禁 |
| 新旧切换 | 首次采用核清、无活动委托、无未知结果、选定范围空仓的冷切换，不做带仓热切核心 |
| 验收 | 同输入、同版本、同决策时间、同事件顺序的行为对照；不是只比较最终盈亏 |

### 1.2 明确不做

不移植 V7/vnpy；不复制 DSV 凭据、账户数据库或整个运行环境；不修改原 DSV 安装；不将回放器或本地撮合器放进正式产品；不实现多策略插件平台；不在重构同时新增报价阶梯、风险预算、次数限制或自动接管外部仓；不把测试通过数量当作原版一致性证明。

“单策略”不等于“单合约”：保留已配置多个品种的业务语义和遍历顺序，不能自行削减为只支持一个品种。

## 3. 为什么不是继续修补

已核对的一个例子是：OnlineTrader 自定义普通撤单30秒超时后升级为恢复屏障，而原包 SDK 普通追单等待与退出清理的30秒超时是两个不同阶段。继续修复这个自定义屏障的计时，只能证明 OnlineTrader 的增强机制自洽，不能证明与 DSV 一致。应先决定此机制是否应存在，再决定修复或删除。来源见 [E01、E06](00-evidence-and-decisions.md)。

同样，新增跳钟门禁后再增加特殊保护执行通路，会形成“为额外限制再维护一条例外路径”的结构。推荐用可证明的正常业务语义替代整个职责簇，而不是删一个布尔判断后继续运行旧状态机。

## 4. 交付成功的可测定义

1. 所有影响交易的分支都关联规则ID；来源不明分支数量为0。未知原版语义必须保持待核，不填常识默认值。
2. 在声明支持的范围内，同输入的决策、目标、报价、数量、时序、拒绝原因和状态变化无未批准差异。
3. 同账户同合约不存在两个发送控制者；对订单和成交的事实约束不因简化而丢失。
4. 日志目录不可写、格式化异常、报表失败和对照器退出，不改变可继续执行的交易决策。关键恢复存储故障单独处理，不与展示日志故障混淆。
5. 新路径不再调用被退役的旧授权、跳钟例外和重复额度机制；通过静态依赖检查及运行轨迹证明。
6. 旧账本保留可读，业务计数与保护状态可解释；任何迁移错误都不会通过“清库重新开始”掩盖。
7. 安装制品、Windows交互、账户断线、交易日转换与原版对跑分别给出证据，不能互相替代。

## 5. 计划实施边界

本目录的 00–04 保留设计提交时的计划与初始状态。每阶段实际完成的模块、取证和剩余条件见实施记录。

现有根目录 AGENTS.md 的“先提交必要事实再发送、未知结果保留占用、界面退出不能删除保护”等约束，在对应ADR和替代验收通过前继续生效。本计划不偷偷改写历史确认文件、不将过去的模拟额度当作新授权、不直接降低现有运行保护。后续实现需同时更新适用的当前开发指引，历史说明保留。

## 6. 推荐执行顺序

`冻结基准 → 规则溯源 → SDK与持久化可行性验证 → 新核心只读运行 → 注入事实对照 → 外围接入 → 状态迁移演练 → 明确授权的在线模拟 → 制品验收 → 冷切换 → 删除旧执行链`。

不预设工期。每一阶段按证据和出口条件推进，不能为了赶进度让待核规则进入交易入口。具体任务和停止条件见02、03、04。
