# 01｜目标架构、接口契约与整段删除方案

返回 [总览](README.md)｜依据 [证据与ADR](00-evidence-and-decisions.md)。所有新路径、类型和接口均为拟议名称，尚未实现。

## 1. 设计边界

### 1.1 保留什么产品

保留一个DSV策略及其全部已确认配置能力，支持原配置中的多个品种；保留账户管理、参数编辑、手工操作、监控、日志和报告等功能的产品入口。各功能能否进入第一阶段切换，由功能对照目录决定，不能把未做的按钮隐藏后声称“只改界面”。

不将本次重构变成另一套通用量化平台。生产代码不包含回测撮合、SDK替身、原EXE提取器或黄金样本生成器。测试可以离线注入输入，这不等于正式产品需要离线交易模式。

### 1.2 四种责任不得混合

| 责任 | 允许做 | 不允许做 |
| --- | --- | --- |
| DSV业务核心 | 用已证输入计算决策、目标和业务状态 | 自行连接柜台、生成额外权限体系、读取日志成功与否 |
| 执行控制者 | 实施目标、接收回报、保持订单数量和身份一致 | 第二次发明策略过滤器、把超时当成撤单成功 |
| 记录与投影 | 持久化必要恢复事实、生成状态/日志/报表 | 因中文格式化或对照器异常改变交易目标 |
| 运维 | 进程存活、校时诊断、磁盘报警、受控部署 | 未核清就重启另一个sender、自动清库或重放开仓 |

## 2. 目标拓扑

```text
Qt桌面（只发命令、只读视图）
           │ 本地IPC
           ▼
单账户交易进程
  command_inbox → session_runner → dsv_business
                         │              │ Decision / Target / StateDelta
                         │              ▼
                         └──── single_execution_controller
                                      │
                                  锁定SDK
                                      │
                                行情/交易服务

              必要恢复记录 → 单writer事实库
                            → 只读视图投影 → Qt
                            → 中文操作日志 / 统计报表
                            → QA复制流（无交易句柄）

Supervisor / 时钟与磁盘诊断：控制部署生命周期，不参与策略判定
```

独立交易进程不是多owner。一个账户由一个有效进程控制，进程中的SDK调用在同一所有者线程/事件循环完成。桌面退出或重连不持有交易对象，也不直接关闭SDK。历史报表从只读连接读取，不抢占交易writer。

## 4. 源码模块去留矩阵

动作含义：保留=职责保留但需检查依赖；拆分=同文件不同职责分别处理；替换=新路径接管后旧路径退役；外移=留在QA/迁移工具；待证=不能仅按名称删除。文件路径以冻结基线为准，最终删除清单由T03静态依赖扫描输出。

| 现有位置/机制 | 动作 | 新去向 | 删除前证据 |
| --- | --- | --- | --- |
| `strategy/entry.py` | 拆分保留已证规则 | `dsv_core/entry_rules.py` | D01–D04/D06/D07逐分支对照 |
| `strategy/risk.py` | 拆分 | `sizing_rules.py`+执行事实检查 | 固定/自动手数及额外字段阻挡区分 |
| `strategy/stops.py`及业务统计 | 保留语义、去重实现 | `business_statistics.py` | 日停、月停、延续与真实盈亏分离 |
| `protection/` | 提取已证归约 | `protection_rules.py` | 理论价、均价、半仓阶段和优先级 |
| `kernel/dsv_strategy.py` | 替换编排职责 | `runner.py`+`transition.py` | 不再混合策略epoch、回补、送单复核 |
| `kernel/engine.py` | 拆分后退役旧执行入口 | 单控制器+必要journal | 每个旧发送/撤单调用已归属新路径 |

| `kernel/day_recovery.py`、`historical_orders.py` | 精简事实核清 | `recovery.py` | 跨日原身份、迟到成交不丢 |
| `kernel/control.py`、`native_control.py` | 替换平台控制层 | `commands.py` | F5/F6/撤单/平仓/全账户操作语义对应 |

## 5. 删除必须遵循完整职责闭包

### 5.1 撤单超时机制

待删除：普通撤单等待达到自定义阈值后引起的全局暂停、上下文撤销、恢复队列加入和附属恢复分支。可保留：单调时间测得的等待时长、告警及诊断事件。必须保留：终态核齐前原单身份与潜在剩余量、迟到成交处理、原版任务退出清理语义。

验收不是“30秒后一定允许重报”，而是“新核心与原版在同终态/成交输入下推进一致；单纯时间流逝不伪造成交或撤单结果”。

### 5.2 跳钟机制

替换单位包括调度器故障标记的交易效果、专门价格保护上下文、特殊派发证明、执行器price_only、重置后的授权和历史重建耦合。正常路径必须已经承担DSV时间判断、订单更新和价格保护后，才能删除。

不能直接让`_fault=False`或让`scope_current()`永远返回True。不能删收盘判断、交易日归属或价格数据校验。若原版跳钟行为不理想，需要修复时单列U型变更，不静默美化基准。

### 5.3 日志体系

运行器只负责产生结构化事件；操作日志为可重建视图。旧回执的`finalized`兼容和扫描布局属于一次性迁移工具，不驻留每轮交易流程。必要恢复事实写入失败不是普通日志故障，必须独立处理。

### 5.4 证明完成删除

每个机制输出：旧符号列表、所有读写点、持久化字段、IPC字段、GUI提示、测试、启动入口、依赖图及替代者。删除后搜索符号无生产调用；旧格式只在只读迁移器中出现。检查打包制品，不只看源码目录。

## 6. SDK选型闸门G1

### 6.1 路线A：复用TargetPosTask，优先验证

目的：由与原版同语义的SDK处理子单追价、撤改和成交等待，产品只表达原版目标及定价回调。

必须完成以下试验后才确定采用：

| 闸门 | 必须证明 | 失败处置 |
| --- | --- | --- |
| G1-A 业务接入 | 原版任务生命周期、offset_priority、价格回调、目标更新方式均可复现 | 不用SDK默认行为凑数 |
| G1-B 持久化 | 明确目标提交、任务创建、子单产生、实际发送、回报之间的崩溃窗口 | 见6.3；不得绕过既有保证 |
| G1-C 归属 | 原账户净仓、双向仓、自有仓、外部仓不混淆 | 无法隔离则不开放此账户组合；不得宣称全量兼容 |
| G1-D 手动操作 | 手动/自动/部分平仓/撤单不构成第二控制者 | 若原版特性需要直接订单，验证有序任务交接，否则否决A |
| G1-E 运行环境 | 完整SDK版本和Python依赖组合可构建；未复制私有运行环境 | 不单文件拼接SDK |
| G1-F 可观测性 | 原生订单/成交身份及目标关联可获取，错误不消失 | 改为B或评估受支持接口，禁止猴补丁无证上线 |
| G1-G 停止重启 | 任务取消、SDK关闭、重连和跨日均有同输入证据 | 不把进程重启当成订单撤清 |

原包SDK会在持续wait_update中推进动作，且默认按账户合约净持仓调仓。此事实来自E01，官方E15/E16只作接口交叉检查。绝不将策略剩余2手直接当成全账户应剩余2手。

### 6.2 路线B：薄的显式订单控制器，条件性备选

仅当A的关键闸门无法满足且有书面结果时采用。保留每子单意图记录和单sender，但删除通用策略身份、重复风控、附加时间屏障和对照依赖。实现原版定价、撤改、等待和数量规则，不把旧ExecutionCoordinator整段改名复制。

B的成本是继续承担子单状态与SDK语义对齐。应有独立原包SDK对照，不能用B自己的状态机生成预期。A/B的选择在G1后冻结；不是运行时可切换设置。

### 6.3 必须显式解决的保证差异

现有内核在子单意图持久化确认后发送。TargetPosTask可能在SDK内部生成子单。**在调用set_target_volume之前只记录一个目标，不等于已在每个子单发送前保存其身份。**

因此G1-B只能得出三种结果：

1. 有受支持且已经验证的接入方式，能保留所要求的发送前事实保证，并不改变原版任务行为；采用A。
2. 只可实现“目标先持久化、SDK子单后观察”。必须把恢复保证变化写入ADR08，列出所有崩溃窗口、对账来源和不可自动恢复情况，经明确接受后采用A。不能称为exactly-once，也不能在报告中继续沿用旧保证。
3. 保证变化不能接受或无法证实，采用B；不以项目已投入大量SDK工作为继续理由。

在决定之前根AGENTS现有约束继续适用。本方案不提前授权弱化保证。研究应先离线故障注入，不能使用真实订单试验崩溃窗口。

## 7. 业务接口契约

### 7.1 输入：BusinessFrame

每轮输入必须区分来源，不合成为“最新全知快照”：

| 字段族 | 必须包含 | 注意 |
| --- | --- | --- |
| 身份 | 会话、账户匿名键、合约、柜台交易日 | 不以本地日期替代柜台交易日 |
| 原生行情 | 原生时间、序号/可用身份、最新价、买卖价量、当日高低、合约规格 | 保留缺失/零/NaN语义，不统一转0或拒绝 |
| 时间 | 本机墙钟、原生行情时间、单调时长 | 三者独立；哪个规则使用哪个由D证据决定 |
| 账户 | 资金字段、实际多空仓、今昨仓、活动单、成交变化 | 不能从净仓反推出毛仓 |
| 配置 | 保存参数、解释后参数、应用边界 | 哈希用于审计，不额外否决正常策略 |
| 原业务状态 | 日/月计数、机会消费、冷却、保护阶段、夜盘参考 | 输入状态版本只用于确定本轮顺序 |
| 更新批次 | wait_update批次、原生对象变化、批内事件顺序 | 原版看到批量末态时，不能擅自逐历史Tick交易 |

状态结构应由原版映射生成，不能先设计通用状态机再强迫原版迁就。

### 7.2 输出：DecisionBatch

建议字段：`decision_id`、`input_id`、`rule_ids`、`state_before_digest`、`state_after_digest`、`actions`、`reasons`、`evaluated_at`、`configuration_id`。每个动作明确是目标持仓变化、直接手动命令还是无动作。候选出现、接受目标、SDK产生订单、发送返回、柜台受理、成交是不同事件。

相同输入和初始状态必须得到相同业务输出。拒绝原因保留第一阻挡和实际执行顺序；可以追加诊断信息，但不能为了“列全原因”执行原版不会到达的副作用分支。

### 7.3 状态转换纯函数

拟议签名：`evaluate(state, frame) -> (new_state, decisions)`。函数不访问网络、系统时钟、文件和旧Kernel。源中依赖当前时间的读取作为显式输入注入；循环内多个时间读取若影响边界，必须在样本中保留其顺序，不能无证合并成一个时间点。

不要假设所有分支都可以只用Decimal重写。源使用二进制浮点、round/int、容差或整数修正的地方需保留实际运算顺序。记录层可用规范化字符串及float64位表示，业务层不因序列化方便改变临界手数。

## 8. 执行接口契约

拟议接口，不是可立即运行的SDK代码：

```python
class ExecutionController:
    def apply_decisions(self, decisions, *, command_id): ...
    def accept_native_update(self, update_batch): ...
    def request_user_operation(self, operation, *, command_id): ...
    def snapshot(self): ...
    def prepare_shutdown(self): ...
```

`command_id`去重的是同一次命令重传，不是禁止原版合法的下一次机会。重复ID同内容返回原回执；不同内容冲突需显式报告。目标版本不可按日志重放自动转为新开仓。

SDK API对象、任务对象和订单实体不暴露给GUI、日志线程、报告线程或QA观察器。所有价格回调读取本轮一致快照/由SDK允许的当前引用，不能在回调中读SQLite、等待GUI或执行NTP。

### 8.1 主循环顺序

循环必须持续驱动SDK，再按取证出的原版顺序推进业务和命令。方案不提前规定“每轮必须先保护后信号”来替代原版顺序；T09/T16需建立真实顺序表。已收到柜台事实应先完整记录到事实模型，不应被日志异常中断。

重计算偏移、下载大历史、导出报表和重建日志不得在热循环执行。新增异步线程只读复制的数据，不获取控制器引用。

### 8.2 一次开仓的可追踪链

`本轮输入 → D规则输出 → 必要记录提交 → 唯一控制器接受 → SDK子单（具体保证见ADR08）→ 原生受理/成交 → 去重入账 → 业务状态及视图更新`。

不能在多层分别用不同时间、不同字段重复执行同一套D规则。派发前必要校验只证明身份、数量、用户是否撤回以及已接受请求是否仍可执行；若因数据变化必须重评，按原版时机和流程进行，并记录原决策替换原因。

## 9. 业务状态与操作状态

建议运行状态：未启动、连接中、运行中、停止新增、核对中、已结束。它们描述用户意图与当前事实，不构成新增策略过滤。DSV自身的日停/月停/几何过滤/冷却应保留独立业务含义，不都塞进“核对中”。

连接状态、用户运行意图、订单事实、保护阶段分开记录。网络断开不等于用户按了停止；用户停止后网络恢复也不能自动恢复开仓。哪一种重连恢复由原版自动执行，由D14证据决定。

持仓阶段不能仅按本地order状态推断。原生多空/今昨仓和逐笔成交应在支持范围内一致。未知订单不得自动当作没有发送；手动“忽略错误”按钮不能清除事实占用。

## 10. 最小存储设计

继续一个writer，建议保留少量明确用途的表/集合，不复制旧通用平台所有投影：

| 集合 | 内容 | 权威性 |
| --- | --- | --- |
| sessions | 代码/配置/SDK版本、账户绑定、启动/退出原因 | 会话审计 |
| user_commands | 命令身份、输入和回执 | 命令幂等 |
| business_checkpoints | D业务状态及输入水位 | 恢复策略状态，不是柜台事实 |
| target_intents | 已接受目标及必要发送前事实 | 按ADR08界定 |
| native_orders | 原生订单身份和状态变化 | 原生证据镜像 |
| native_trades | 原生成交身份、数量、价格、时间 | 去重事实；冲突不覆盖 |
| events | 决策、异常和关键生命周期 | 可读日志和报表来源 |

主键不能只用未经核对的trade_id。先核对provider/account/exchange/trading-day/order维度中的真实唯一性，再决定组合键；原始ID原样保存，内部哈希只是索引，不丢可逆证据。

不在新库复用旧表名以假装兼容。存储版本独立；旧库只读。必要状态的checkpoint与对应事件水位要在同事务内保存，避免“分钟已消费但目标未记录”或相反的撕裂。

## 11. 存储失败与日志失败区别

| 故障 | 预期处理 |
| --- | --- |
| 中文格式化失败/展示日志目录只读 | 记录诊断，保留原结构化事件，不影响原业务决策 |
| 比较文件失败/外部DSV日志不在 | 观察能力降级，不撤回已接受目标 |
| 报表导出失败 | 返回导出错误，不进入交易恢复 |
| 必要状态提交失败 | 不把未记录的新目标交给控制器；明确告警并进入经过验收的恢复路径 |
| 已有SDK任务在必要存储失败前已接受目标 | 必须有单独演练的责任策略，不能声称停止接受新目标就阻止SDK剩余子单 |
| 不可恢复的事实库损坏 | 不启动替代sender、不重放目标；保留原进程与柜台状态，按明确应急流程处理 |

最后两项是I型运行边界，不是DSV策略公式。实现时必须说明原任务、未成交开仓量、平仓保护和用户紧急命令分别如何处理。只写“fail closed”或“保护继续”不合格。

## 12. 时间和日历

三类时间独立：D业务时间按原版；SDK原生时间用于对应行情/订单；单调时间用于技术等待与耗时观测。额外诊断计时不得自动创造业务日停。

不将单调推算的UTC直接冒充交易所时间。跨午休和夜盘交易日不能使用本地零点重置。连续运行不是强制同一SDK连接无限存活；受控重启必须以原版行为、未结订单和官方版本约束为依据，详见04。

用户自动校时作为U01独立组件：不在SDK线程执行提升权限、系统命令或NTP请求；记录调整前后偏差、权限结果和复测。初版优先在无未结状态的维护窗口执行。有仓自动调整若未通过同输入和异常验收，不开放该运维能力，不能声称已经完成全天自动校时。

## 13. 行情、历史和回补

每项D规则列出必需数据：当前报价、当日高低、原生分钟K线、夜盘尾部、指定日线等。只为这些数据建立就绪判断。不能要求所有品种从开盘起拥有完整逐Tick历史，除非原版规则确有此要求。

历史用于观察状态重建，是否消费机会必须跟原版；当前已证的仅观察回补不得制造成交或执行历史开仓。真实已接受机会不能因重建而清空。批量历史尾笔和真正实时新事件必须区分，不能用“最后一条就是实时”作为无条件假设。

用于恢复保护的价格输入与用于新开仓的完整业务输入可有不同需求，但差异应来自原版分支或明确I要求，不复制另一套临时保护策略。

## 14. 手工交易与账户范围

T10必须列出：手工开多/空、减仓、全平、撤本策略委托、撤全账户委托、停止策略、关闭窗口、账户切换。每项对应原版入口、实际副作用和与自动任务的关系。

若采用TargetPosTask，不能让旧GUI直接insert_order。同合约存在任务时，手工操作只能经被验证的目标调整或有序任务交接；取消任务可能撤原单，不能把它作为无副作用的“暂停”。

存在外部仓时，先核对DSV实际接管范围。首个离线/模拟验证可在干净选定合约开展，但这只是测试边界，不是产品擅自取消混合仓功能。未解决该项不能签署完整功能兼容。

## 15. 性能与线程边界

先在冻结机器和输入集测量，不给未经测试的速度承诺。记录行情接收至业务评估、目标接受、SDK动作、回报记录及UI展示的独立耗时，报告P50/P95/P99和最大值。业务事件不能为降延迟而丢弃；UI行情刷新可以合并但不可作为业务输入源。

验收原则：关键路径延迟相对双方冻结基线无未经解释的退化；最长无SDK推进间隔、队列积压和IO停顿都可观察。绝不能通过移除终态等待制造“更快撤改单”。

## 16. 旧平台退役条件

所有发送入口已转移；GUI不再导入旧Kernel；新core不导入旧scheduler/control；旧state字段只有迁移器读取；安装制品无两个可激活sender；旧PR测试已经按D/U/I/X分类；回滚工具不依赖从旧运行路径偷拿当前交易对象。

只有满足这些条件，删除旧执行链才算完成。将旧代码留在新运行器内部，通过多个兼容开关控制，不算本计划的目标架构。
