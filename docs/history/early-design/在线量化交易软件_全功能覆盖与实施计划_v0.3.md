# 在线量化交易软件全功能覆盖与实施计划

版本：v0.3  
日期：2026-11-09，Asia/Shanghai  
产品暂名：OnlineTrader  
状态：本轮功能范围与实施顺序定稿；具体交易规则、生产参数和接入授权分别确认，尚未开发新产品。

建设独立的 Windows 在线自动交易软件，覆盖策略 PDF 与本次识别的 DSV 产品能力。功能可以采用新的界面、技术和运维机制实现；每项能力都必须有入口、完整业务流程和验收证据。不能以默认关闭、留一个按钮或具备 SDK 类名代替功能完成。

本轮交付仅为清单和实施计划。新工程拟使用独立目录 `E:\online-trader`，尚未创建；V7 rc.41 保持冻结。本轮不修改 V7 产品代码，不安装服务、不连接账户、不报撤单，也不恢复云端 CI/CD。

## 一 规格关系与覆盖口径

本文件是新产品的功能范围、实施顺序和交付判定入口。[v0.2 技术设计](https://github.com/Yoruto/Futures-Trading-Assistant/blob/a6cc369c86ada924e26dce369a9dbfe87ffa55bc/docs/%E5%9C%A8%E7%BA%BF%E9%87%8F%E5%8C%96%E4%BA%A4%E6%98%93%E8%BD%AF%E4%BB%B6_%E5%BC%80%E5%8F%91%E8%AE%BE%E8%AE%A1%E8%AF%B4%E6%98%8E%E4%B9%A6_v0.2.md)继续作为架构基线；其候选关闭项在本文件中明确为最终必交付功能。两份文件出现范围差异时，以本文件的显式补充为准；交易行为以单独获批的[规则裁决表](在线量化交易软件_规则裁决表_v0.3.md)为准。[v0.1](https://github.com/Yoruto/Futures-Trading-Assistant/blob/a6cc369c86ada924e26dce369a9dbfe87ffa55bc/docs/history/online_trader/%E5%9C%A8%E7%BA%BF%E9%87%8F%E5%8C%96%E4%BA%A4%E6%98%93%E8%BD%AF%E4%BB%B6_%E5%BC%80%E5%8F%91%E8%AE%BE%E8%AE%A1%E8%AF%B4%E6%98%8E%E4%B9%A6_v0.1.md)保留历史，不再作为并行实施标准。

**全覆盖的边界：**覆盖在线策略、账户、人工交易、参数工具、展示报表、通知、授权和运维。保留单账户执行、单套正式策略、多白名单品种的首版边界；可保存多个账户档案，任一时刻只有一个账户/通道拥有本实例交易权。多账户同时自动交易、多策略市场、离线研究、历史回测、参数寻优和 AI 自主下单不在本产品范围。缓存参数重算、必要的历史展示和开发故障事件不等于增加离线交易产品。

不照搬原软件的资金风险缺口、全账户隐式撤单或停止后悄然丢失保护等行为；替代机制须保留原使用目的并独立验收。商业设备激活与交易授权是两种权限，任何软件授权故障不得删除已有持仓保护。

PDF的11合约参数表与本会话读取的桌面5合约配置是不同快照，例如单笔风险比例分别写0.3%和0.2%。两者都不是新产品已批准的生产默认；不得从材料自动创建上线名单、资金预算或交易授权。

## 三 规则定稿与明确替代

功能范围已包含全部可选策略能力。B01–B20 的解释仍保留在[规则裁决表](在线量化交易软件_规则裁决表_v0.3.md)，后续以一份完整版本确认，避免开发中逐次猜测。

优先处理五组会改变交易行为的决定：

1. **仓位与零值：**预算不足一手是否拒开，固定/自动/兜底量是否共用硬闸门，0值的模式语义。推荐统一拒绝超预算增仓，不照搬 DSV 算得0手却保留保证金手数的路径。
2. **入场时序：**延续开与开盘禁开、同K线机会、滞回路径、双价追单及80%/90%冲突。保护观察不能被入场去重节流。
3. **退出优先级：**80%保护、移动、半仓及二阶段、收盘和账户紧急动作的关系；明确奇数手、只剩一手和同时触发。
4. **价格与记账：**理论价冻结、实际均价、名义点数、真实资金损益、滑点和费用分别定义，部分成交首次即保护。
5. **日切与异常：**禁开何时解除、180秒断流、5秒检查、报单计数、人工活动及自动恢复授权，分别写出条件与结果。

下列行为属于明确提出的安全替代，仍须写入新产品规格并测试：普通停止仅撤自身可证明归属的开仓残单；停止新开仓不停止已有保护；原策略失权不删除计划；算法0手不能翻译为自动/最少1手；全断网下只能报告未能送达或未成交。账户级撤单、人工接管及停止内核保留显式入口，不隐式扩大操作范围。

软件许可到期只能影响许可范围内的新增权限，不得撤销已登记保护。未获批规则的功能可以完成开发测试，但不得被生产配置自动启用。默认关闭的半仓、延续开、二阶段、移动等也必须完成开关两侧验收，才能标记功能完成。

## 四 架构与技术选择

采用 v0.2 的职责边界：控制台、可替换开仓策略、常驻执行与保护内核、守护与更新器。订单、资金预占、实际持仓、保护锁存和权威账本属于内核；关闭GUI或更新策略不结束原持仓管理。SDK、OMS或保护解释器本身故障时，不承诺还能正常保护；故障状态必须准确显示并可接管。

Python、PySide6、SQLite和受限IPC是当前推荐方案，不是功能要求。精确版本由新工程兼容矩阵确定；不继承 DSV 发行包或 V7 虚拟环境。TqSdk生态作为优先试点，TqAccount/TqCtp/原生CTP的选择在接入验证后定版，正式部署只允许一条获批通道拥有自动交易权。更换技术需保证本清单中的状态、身份、保护和验收语义一致。

接入试点必须尽早进行：官方 [TqCtp 文档](https://doc.shinnytech.com/tqsdk/latest/reference/tqsdk.tqctp.html)列出额外包及向期货公司申请的连接信息；[TqSdk程序结构](https://doc.shinnytech.com/tqsdk/latest/usage/framework.html)说明其数据推进及默认本地模拟行为。不能先把登录成功当作完整核对通过，再在后期发现无法证明恢复。Windows服务/GUI隔离参考 [Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)；持久化参数以 [SQLite 官方说明](https://sqlite.org/pragma.html#pragma_synchronous)和目标机器故障试验共同确定。

只保存多个账户档案，不在首版引入多账户并发执行。参数计算可以读取明确标注的参考历史，不把历史展示或缓存值注入真实执行行情。V7 只参考已有工程经验；若复用源码，必须登记来源提交、许可、依赖和新工程重验结果。
