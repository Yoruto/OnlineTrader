## 0. 方案摘要

用户期望软件开机自启动、在国内期货交易时段自动运行、内置交易日判断、启动时检查更新，并且不因省电、普通自动睡眠或后台任务条件而意外停止。

采用“后台常驻、按合约时段调度、交易责任持续管理、维护窗口更新”的实现。后台启动不等于立刻开仓，关闭窗口不等于结束交易，休市不等于清除订单责任，电源切换不等于暂停策略。

三条优先级必须贯穿所有入口：

1. 已有订单、持仓和不确定报单的恢复，优先于常规更新安装。
2. 人工暂停及策略既有停开状态，优先于自动启动。
3. 合约的有效交易窗口与真实账户事实，优先于固定钟点表和界面状态。

不扩展策略数量，不迁移交易框架，不新增第二个发送者，不通过放宽账户绑定、删除旧账本、清除 UNKNOWN 或修改日停规则实现“自动运行”。正式产品完成后，部署只选择一条已验收执行链；迁移期间两条链分别验证，不能同时操作同一账户。

## 1. 用户需求、默认值与产品边界

### 1.1 需求追踪

| ID | 用户需求 | 开发落点 | 验收重点 |
| --- | --- | --- | --- |

U04 的安全细化为：每次后台启动安排更新检查；不适合安装时记录并延后，不能阻塞已有责任恢复，也不能为了更新自动平仓。此细化是本计划的设计选择，应在设置说明和验收中明确，而不是让用户误以为“每次启动必先升级”。

| 设置 | 新安装建议默认值 | 明确语义 |
| --- | --- | --- |

“默认开启”只是产品偏好，不自动选择账户、不读取其他软件凭据、不从旧有限授权扩展出无限交易权限。首次设置应展示运行范围和恢复规则，由用户一次确认；合法运行计划内不要求每天重新弹框。

升级现有用户时保留已有关闭项和暂停状态。无法区分旧用户意图的字段标记为待确认，不用新默认值覆盖。取消开机自启动仅影响后续拉起；取消自动运行同时持久禁止以后自动新开，不自动终止已有持仓管理。

### 1.3 非目标与现实边界

7×24 指后台可长期待命、恢复并按批准计划工作，不指全天开仓或永不需要维护。本文不授予真实资金交易、连接账户、安装服务或改变操作系统的执行权限。

不能用软件保证电池耗尽、断电、过热保护、强制关机、系统故障或用户主动睡眠时仍然执行。必须提前告警并设计恢复；不关闭危急电量和硬件保护，不伪报本地止损在进程退出后仍受保护。

第一版不做双机双活、不做运行中交易引擎热替换、不自建 NTP 校准时钟，不恢复已按用户要求关闭的 CI/CD。开发、故障注入和长稳测试均通过本地命令及受控测试机进行。

## 3. 架构与职责

### 3.1 进程结构

```text
Windows 系统启动
    └─ 后台宿主 / Supervisor
          ├─ 运行计划、日历调度、重试预算、健康检查
          ├─ 选择一个已验证版本并启动/附着执行器
          └─ 更新检查与维护协调（无交易发送权）
                    │ 受控 IPC
                    ▼
             交易执行器 / 单 owner
             账户锁 → 同步/恢复 → 原策略与订单控制器
                    → 事实提交 → SDK 派发

Windows 用户登录
    └─ 工作台 / 托盘 → IPC 附着；关闭界面不关闭 owner

签名更新安装器
    └─ 仅在维护互斥、执行器已退出且责任核实后切换程序版本
```

Supervisor 不导入策略报单入口，不调用 SDK 下单/撤单，不改 Journal 的订单、成交、占量或授权绑定。交易命令继续经过原控制协议及 owner。更新安装器不携带交易凭据。

### 3.2 宿主选择

正式无人登录方案优先采用 **Windows SCM 自动启动的轻量后台服务**，界面使用独立登录启动项。SCM 支持系统启动时拉起服务；服务与交互桌面通过受限 IPC 通信，不在 Session 0 弹出 Qt 登录窗口。[R01][R02]

服务只承载薄宿主和现有 Python 执行器，不重写策略。宿主采用经过锁版和打包验证的服务适配层；实现阶段需提交依赖、许可证、签名和冻结制品兼容性清单。服务启动应快速报告阶段，网络或账户同步在受控工作流程中推进，不能长时间阻塞 SCM 启动回调。

保留任务计划程序方式用于兼容部署和前期验证，但不得与服务同时监督同一部署。非交互任务在节电模式下可能延迟触发，因此不能只修改电池两个选项就承诺任何环境下准时启动。[R03] 实机未证明符合 U01/U05 的兼容模式标记为“登录启动/受限部署”，不得显示完整全天候验收通过。

### 3.3 单实例、锁和交接

保留现有全局 AccountLock。另增加部署级 Supervisor 单实例锁和维护门闩，名称基于稳定 deployment_id，不随版本目录变化。锁与控制管道 ACL 仅允许指定运行身份及受控管理身份；现有锁访问被拒绝是阻断，不是绕过理由。[C02]

普通启动先短暂取得维护门闩，检查是否维护中，登记启动尝试，再由执行器取得账户锁并返回已绑定身份。维护流程先取得门闩阻止新启动，再请求 owner 正常停机；确认进程退出及账户锁释放后才能检查/迁移数据。owner 正常关闭不能反向等待维护门闩，避免死锁。

所有进程身份至少包含 PID、创建时间、boot/run 标识、实际镜像路径和版本摘要；PID 单独不足以认定同一进程。新实例必须重新取得原账户锁。监督器崩溃、超时或看不到心跳不能据此抢锁、清库或再创建一个发送者。

## 4. 配置、运行计划与用户意图

### 4.1 三类状态分开保存

| 类别 | 主要字段 | 写入责任 |
| --- | --- | --- |
| 部署偏好 | 自启动、UI 登录启动、更新渠道、防睡眠偏好、已验证宿主身份 | 受控设置/部署协调器 |
| 长期运行计划 | plan_id、revision、账户引用、执行器类型、配置哈希、合约范围、运行时段、恢复许可 | 用户明确确认后的计划存储 |
| 运行与暂停状态 | 当前交易日、会话、手工暂停锁存、调度回执、恢复状态、未完成责任 | 原 owner 与协调器各自单写存储，通过回执同步 |

部署偏好和运行计划不是交易事实库的替代品。计划存储可使用单独的小型事务库；不承诺跨两个 SQLite 库天然原子。通过同一 command_id、revision 和持久回执完成可恢复交接。

拟议示例仅示意偏好，未绑定账户时必须保持待配置：

```json
{
  "schema_version": "OT_ALWAYS_ON_SETTINGS/1",
  "start_at_boot": true,
  "show_tray_at_logon": true,
  "automatic_strategy": true,
  "preparation_lead_seconds": 600,
  "automatic_reconnect": true,
  "power_profile": "ALWAYS_ON",
  "update": {
    "check_on_start": true,
    "channel": "stable",
    "install_policy": "VERIFIED_MAINTENANCE_ONLY"
  },
  "active_plan_id": null
}
```

600 秒是初始建议值，需测试后确定；不是 DSV 开盘等待参数。设置默认值不能转化为已完成注册、已读到凭据或已有有效授权。

### 4.2 人工暂停与自动调度

手工暂停新增开仓默认锁存到显式恢复，跨进程重启、断线、午休、日切和版本更新保留。另提供“暂停到下一交易窗口”的明确操作；不能让普通暂停隐式变成这个行为。

暂停命令先持久记录禁止自动启动的意图，再向 owner 发送原停止新开命令，收到回执后显示已执行；通信失败显示“已禁止自动启动，当前执行器停止待确认”。恢复命令以新 revision 和实际账户/配置复核完成，不能仅删除一个暂停文件。

设置“自动运行关闭”、手工暂停、策略当日停开、维护停机是不同原因。自动调度不能重置日停、分钟消费、目标次数、冷却或未完成退出目标。暂停新开不代表终止持仓保护，也不等于所有原挂单已撤；是否撤开仓残单继续按原配置与实际回报处理。

### 4.3 长期计划与当前有限授权的衔接

当前替代链绑定有限 grant，重启及日切有明确停开约束。[C04] 全天候功能必须新增版本化的“长期计划 → 当日运行授权”协议，而不是反复伪造桌面 F5、覆盖 grant 文件、删除 SDK_SCOPE_BOUND 或重建空库。

每份当日授权绑定计划 revision、账户、执行器、profile/calendar 哈希、交易日、允许合约、既有额度和有效窗口。同账户同交易日重启复用业务配额与责任；新进程、新 grant ID 或下载更新不能重置当日目标计数。

计划变更影响已有持仓时，不直接重算旧目标。只改变后续新目标，或通过已明确支持的独立变更命令处理。超出原计划范围、未知账户事实、旧授权无法安全衔接时明确待复核；不能为了全天候放宽所有检查。

## 5. 状态模型与启动流程

### 5.1 不使用一个 running 布尔值表达所有状态

运行状态建议为 `BOOTING / WAITING_CONFIGURATION / STANDBY / PREPARING / RECONCILING / RUNNING / RECOVERING / MAINTENANCE / NEEDS_REVIEW / STOPPED`。

另保留独立维度：用户新开意图、策略日停、行情质量、交易通道、事实同步、存储健康、电源保障与更新阶段。已有责任是否受管理应单独显示；不能因为授权暂停就显示“无持仓风险”，也不能把 NTP 诊断失败等同于所有执行失效。

### 5.2 启动顺序

```text
取得宿主单实例并验证部署身份
    ↓
检查是否有旧执行器：有则验证身份并附着，不能重复登录
    ↓
读取暂停意图、运行计划、维护事务、上次退出及责任摘要
    ↓
责任未完成 / 非正常退出 / 信息不可确定？
    ├─ 是：用兼容且已验证的现有版本优先进入恢复
    └─ 否：允许在维护条件满足时先安装已验证稳定更新
    ↓
加载有效配置与缓存日历，建立电源保障，安排非阻塞更新检查
    ↓
交易窗口或盘前准备窗口内？
    ├─ 否：后台待命并保持必要恢复/诊断
    └─ 是：准备连接、同步及策略恢复
    ↓
检查计划、人工暂停、日停和原策略条件，再允许新开
```

本地责任摘要只用于决定“先恢复还是可能进入维护”，不能证明柜台已经空仓。信息缺失按需要核对处理。第一次网络不可用时进入有界重试，不因为 Windows 刚启动还没联网就永久退出。

### 5.3 停止和退出

“退出工作台”只退出 UI；“暂停自动新开”保留后台与已有责任；“停用开机启动”只影响后续启动；“停止后台/维护停机”必须展示未完成责任和实际退出条件。

正常维护关闭必须由 owner 完成状态提交和资源关闭，不能由 GUI 直接终止 Python 进程。用户或系统强制结束无法保证被应用阻止，重启必须识别为非正常退出。不得在系统关机通知里假定仍有足够时间等待成交或一定能平仓。

## 6. 交易日历与按时段自动运行

### 6.1 以合约时段为单位

内部保存 UTC，交易时段解释统一北京时间，不依赖宿主显示时区。每段至少保存 exchange、contract、session_id、open/close、auction 边界、cabinet trading_day、是否原策略开盘段、是否实际清仓终点、来源版本和覆盖范围。

必须区分日盘、夜盘、跨午夜、集合竞价、午休和最终收盘。不把 00:00 当交易日切换，不把每次 session_close 当强平时点，不把调休工作日当交易日。TqSdk 的夜盘字段可能以 25:00 等形式表达次日时刻；其交易日历与时段接口需按项目锁定 SDK 的实际能力验证。[R09][R10]

### 6.2 来源与例外

复用 TradingCalendar 及现有 metadata 构建路径。交易所发布的交易安排是例外安排依据；SDK 合约时段和交易日历提供可用数据，但不能从“当天交易”推导出“当晚一定有夜盘”。

固定回归示例可使用上期所 2026 年安排：9 月 30 日日盘与当晚无夜盘需分别表达，部分调休周末仍休市。[R11] 这些日期只作带来源的测试夹具，不能硬编码为未来生产日历，也不能把一家交易所的规则无条件套给全部合约。

缓存应携带 coverage_start/end、source_id、fetched_at、公告/数据摘要、解析版本、例外清单和是否完整。更新采用校验后原子发布，失败保留上一份合格缓存；日历变化影响已计划窗口时，以 session 身份与计划 revision 幂等重算。

有效缓存仍覆盖当前窗口时，一次下载失败不应暂停整个系统。当前合约无可信覆盖或来源冲突时，不猜测自动新开，明确受影响范围；已有订单与持仓责任继续保留，允许的核对与撤单不能被无关日历错误遮蔽。

### 6.3 调度语义

| 场景 | 拟实现行为 |
| --- | --- |
| 盘前窗口 | 提前连接、订阅、恢复、核对；不绕过 DSV 开盘等待和竞价配置 |
| 开盘正常到达 | 已就绪则按原策略运行，不保证必须产生订单 |
| 09:17 等时段内启动 | 完成核对后使用当前数据；不补发错过的历史信号 |
| 午休与恢复 | 原交易日状态保留；恢复不重置计数、分钟消费或日停 |
| 各合约交易时间不同 | 逐合约控制活动状态；一个合约休市不错误停掉全部其他合约 |
| 周末或节假日 | 后台待命、诊断、备份/更新；不自动运行新增交易 |
| 夜盘跨自然日 | 按完整会话和柜台日继续，不按零点清理状态 |
| 下一交易日 | 核对柜台日并执行已证明的日切；按长期计划创建/恢复当日授权 |

启动回执键应包含 plan_id、revision、账户、交易日和 session_id。重复触发、UTC 倒退、宿主重启不得重复建立目标。错过周期只重新评估当前状态，不追赶执行历史交易动作。

## 7. 恢复、重连与监督

### 7.1 健康证明

owner 完成一轮推进后发布 heartbeat sequence、owner_boot_id、engine/version、最近成功 SDK 驱动、最近事实同步、状态提交进度、未完成责任数量和实际阶段。休市无新报价不等于 owner 卡死；GUI 线程或独立心跳线程活着也不能代替 owner 推进证明。

监督器在本机记录收到新序号的单调时间，使用它判断停止推进。不要拿异机单调值比较，也不要仅依赖会跳变的 wall_time。心跳采用有界、原子快照，不能每个 Tick 同步写一份巨大状态文件。初始可用 5 秒发布、20 秒疑似告警作为测量起点，需按真实启动阶段和时延分布调整，不是硬实时保证，也不是超时即杀进程条件。

### 7.2 故障分类

| 事实 | 自动处理 | 禁止处理 |
| --- | --- | --- |
| 网络断开，owner 仍推进 | 使用 SDK 已有恢复能力；必要时单 owner 受控重连，再核对 | 网络抖动即启动另一个 owner |
| 进程已确认退出 | 留存退出证据，按预算重启同一责任恢复链 | 从空配置/空账本启动 |
| PID 存在但无推进 | 标记 HUNG_SUSPECT，诊断、告警及受控停止请求 | 仅凭心跳超时抢账户锁或并发拉起 |
| 认证失败/权限不足 | 限制重试、告警，等待凭据修复 | 持续快速登录或回退到其他账户 |
| 存储失败/归属冲突 | 保留原故障与责任，进入明确复核状态 | 清除失败标志、删账本、假装提交成功 |
| 休眠唤醒/长时间无调度 | 重新核对当前时段与事实后处理到期责任 | 补发所有错过的撤改单周期 |

重试建议从 1、2、4 秒递增并上限 60 秒，加入小幅抖动；崩溃可先采用“10 分钟内 5 次”告警升级预算。以上是待测运维默认值，须持久保留预算并区分计划维护退出，不得通过重启监督器清零形成风暴。

预算耗尽不等于订单已结束。无法恢复时必须显示“执行器未恢复，保护不可确认”并升级告警，不能继续显示保护中。后续有限恢复尝试与人工介入规则需显式配置，不进行无界密集循环。

### 7.3 不确定与迟到事实

继续遵守：报单超时不等于拒单，撤单请求不等于撤单成功，查询暂未找到不等于绝对不存在。恢复先接受已取得的原生事实，再处理超时目标；同轮部分成交与超时按既有订单责任语义核对。

Supervisor 重启不应杀死仍健康的执行器。重新附着失败时先诊断身份和 IPC，不能按进程名批量终止。同一账户原 owner 未确认退出时，任何恢复/更新启动都不能形成第二个发送者。

## 8. Windows 部署与任务配置

### 8.1 实际运行身份

服务或非交互宿主使用经过验证的指定账户及最小权限。首次配置在该运行身份下验证用户配置目录、凭据读取、网络、程序/数据目录权限、IPC 与账户锁访问。不能假设切为 SYSTEM 后原 WindowsVault/DPAPI 凭据仍可用。

需要 Windows 登录密码时由系统的受保护注册接口管理，不写入配置 JSON、批处理、日志或 Git。账户密码变更/到期、登录权限变化应成为部署健康项。服务账户的安全上下文及密码有效性会影响启动，需实机验证。[R04]

任务模式不得把 S4U 当“无密码又具备全部访问”的通用替代：官方文档指出其网络及加密文件访问限制；交互令牌模式则要求用户已登录。[R05]

### 8.2 兼容任务模式的必选项

| 项目 | 配置要求 |
| --- | --- |
| 后台触发 | 要验证未登录启动时使用系统启动触发；GUI 另用登录触发 |
| DisallowStartIfOnBatteries | false |
| StopIfGoingOnBatteries | false |
| RunOnlyIfIdle | false |
| IdleSettings.StopOnIdleEnd | false |
| ExecutionTimeLimit | PT0S；同时检查触发器级时限和任务 EndBoundary |
| MultipleInstancesPolicy | IgnoreNew，不能 StopExisting 或并行执行 |
| RunOnlyIfNetworkAvailable | 不作为后台启动前提；由后台处理未联网 |
| StartWhenAvailable | 按启动补偿需要开启，业务命令自身幂等 |
| Automatic Maintenance | 不把交易后台设置成空闲维护任务 |
| 行为与工作目录 | 固定启动器绝对路径，明确工作目录和数据根，严格参数引用 |

微软文档的默认 72 小时限制可由 PT0S 取消。[R06] 基线旧脚本已设置无限时长和正确电池选项，应保留，不作为新增缺陷重复计算。[C01]

节电模式对触发的限制需独立验证。[R03] 服务模式并不豁免系统睡眠、电量耗尽和硬件限制；只有第 9 节真机条件同时满足，才可标记该设备支持全天候部署。

### 8.3 安装、取消与迁移

安装流程必须记录部署 ID、宿主类型、已注册任务/服务身份、旧设置、预期和实际配置。取消时只撤销本部署登记的对象，不能删除所有同名 Python 任务。

提供只读检查、经确认修复、停用三个入口；不要每次 GUI 启动都静默请求管理员权限或重装服务。管理员安装组件与日常普通权限 owner 分离。

旧便携版守护迁移后，应验证登录、注销、远程桌面重新连接和升级目录变化都不会额外拉起旧执行器。界面应显示“已请求开启 / 注册成功 / 实际可用 / 需要管理员处理”，不能只有勾选状态。

## 9. 电源与防意外停止：强制验收范围

### 9.1 基本原则

AC 表示接电，DC 表示电池供电。两种情况下，拔插电源、无人操作、锁屏和最小化都不能让软件主动放弃订单/持仓管理。电源变化可告警和延后非关键下载，不能自动暂停策略、平仓、结束 owner 或重置运行计划。

休市、周末和人工暂停新开期间，只要全天候后台仍被用户启用，继续维持待命所需电源保障。完全停用后台后的释放与系统设置恢复另行执行，不能由关闭 UI 触发。

### 9.2 三层保障

| 层 | 实施要求 | 成功证据 |
| --- | --- | --- |
| 系统配置 | 核对并经确认配置 AC/DC 的闲置睡眠、普通定时休眠、合盖需求及节电模式 | 修改前后实际值、策略覆盖状态和权限结果 |
| 应用请求 | 后台持有系统/执行保持请求，必要生命周期正确释放 | API 结果、句柄生命周期、可读取的请求状态 |
| 硬件验证 | 实际设备在目标电源/待机组合下运行 | owner 序号、SDK 驱动和责任处理持续推进的记录 |

使用 powercfg 等系统接口查询待机类型、活动电源方案及 AC/DC 项；不能只看到“高性能”方案名字就认定通过。[R07] 不全局禁用所有休眠能力或危急电量保护，不通过常驻鼠标模拟或循环按键冒充工作负载。

### 9.3 后台电源请求

优先封装 `PowerCreateRequest / PowerSetRequest / PowerClearRequest`，在平台适用时申请 `SystemRequired` 和经验证的 `ExecutionRequired`。owner 活跃时自行持有请求，Supervisor 待命时持有必要请求；避免监督器退出把仍运行 owner 的唯一保护一并释放。每个进程管理自己的引用计数和句柄，不反复 Set 却不 Clear。

API 失败应立刻显示 POWER_PROTECTION_DEGRADED，不能声称已保护，也不能因此直接杀掉当前交易执行器。默认不要求显示器常亮；如特定硬件只有常亮才能通过测试，应作为设备限制明确展示，不能暗中改变。

微软指出：现代待机设备在电池供电时，相关请求可能在系统睡眠超时到期五分钟后被终止；用户主动睡眠也有明确限制。因此单个 API 成功不是无条件不睡眠的证明。[R08] SetThreadExecutionState 的备用实现同样不能阻止所有用户主动睡眠。[R12]

### 9.4 设备适配与安全恢复

部署检查记录 S3/Modern Standby、Windows 版本、电源来源、节电状态、活动方案、显示器超时、睡眠/休眠超时，以及需合盖运行时的合盖设置。

现代待机设备必须单列 DC 熄屏、锁屏、合盖及节电组合。不能通过反复续申请、未经支持的注册表绕过或关闭系统安全功能宣称解决。无法满足目标组合的设备标记为受限，不授予“AC/DC 全场景全天候通过”；可改用经过验证的运行方式或设备，再重新验收。

电源配置变更前保存原值，退出全天候部署时仅恢复仍等于本程序设置的项目，避免覆盖用户之后的修改。组策略/OEM 程序覆盖设置时如实告警，不反复与系统争写。

低电量提前告警；阈值作为部署参数测试。危急电量、过热与电源最终中断时，不承诺继续交易；在系统允许的时间内保留已提交事实，重启进入恢复。测试不得在真实资金持仓下故意耗尽电池。

## 10. 自动更新与维护状态机

### 10.1 检查、下载、安装分离

```text
IDLE → CHECKING → AVAILABLE → DOWNLOADING → VERIFIED
                                      ↓
                                  DEFERRED
                                      ↓ 满足维护条件
QUIESCING → OWNER_EXITED → BACKED_UP → SWITCHED → VERIFYING → ACTIVE
                                                     └─ FAILED / COMPATIBLE_ROLLBACK
```

启动检查在非交易线程进行，有总超时和退避；临近准备窗口或需要恢复时，不等待下载结束。初始建议检查总预算 3 秒、已下载更新至少距下一准备窗口 15 分钟才考虑安装；均为待测部署默认值，不是可靠完成时间承诺，实际还需覆盖备份和健康验证预算。

网络失败、无新版本、更新服务器故障不阻止旧稳定版本启动。电池时默认不取消已运行交易；可按偏好延后大文件下载。仅跟随经过发布验收的 stable 制品，不把 GitHub main 新提交等同于可安装版本。

### 10.2 自动安装的必要条件

必须同时满足：有效维护窗口；无当前或临近交易准备任务；本程序所有受管理账户无持仓责任、未决订单、UNKNOWN、待对账冲突或未完成退出；取得维护门闩；owner 正常退出；安装空间与备份验证通过；版本和数据兼容性已确认。

柜台无法核实、运行摘要过期或责任不明时，延后自动安装，不把“进程不存在”解释成账户空仓。不要扫描或平掉不属于本程序的外部仓位；发现外部活动影响范围时记录并延后维护复核。

安装等待中重新临近开盘时，尚未切换则取消本次安装并继续原版本准备。已开始不可中断迁移时不启动交易进入半成品状态；明确维护超时告警与恢复步骤。没有任何更新流程可以把计划预算当成已完成事实。

### 10.3 更新真实性与兼容性

发布清单至少包含 release_id、版本、渠道、源提交、平台/架构、每文件大小与摘要、最低启动器版本、账本和配置读写兼容范围、迁移策略、签名及签名密钥身份。

使用成熟签名库和固定可信发布根；验证 HTTPS 之外还验证签名、长度、摘要、版本策略及目标平台。不能把来自同一下载源的 SHA256 当作独立身份认证。密钥轮换、撤销和回滚版本策略需要明确；TUF 可作设计参考，但本项目未实现 TUF 协议前不得声称具备其全部防护。[R13]

不在客户端嵌入仓库写入 token 或个人访问 token。需要私有发行读取时，另行配置最小只读访问与撤销机制。未验证的压缩包不得运行代码；解包限制路径穿越、链接、覆盖范围、文件大小和数量。

### 10.4 文件布局与失败恢复

稳定 launcher/host 与版本目录分离，配置/凭据引用/账本/日志放在明确的数据根。更新不能依赖当前工作目录，也不能以版本目录变化改变账户身份。

```text
安装根/
  launcher/                 稳定启动器与宿主
  versions/<release-id>/    不可变已验证程序
  staging/                 未激活下载，不能直接执行
  current.json             原子切换的版本指针
数据根/
  operations/              运行计划、暂停意图、维护日志
  accounts/                既有账户数据，迁移须显式
  backups/                 校验过的一致性备份
  logs/                    脱敏运行证据
```

每个更新阶段先登记持久状态，崩溃后根据实测文件和进程状态恢复，不根据“上次日志说成功”跳步。安装完成后的首次启动先验证解释器/依赖/入口/存储兼容/IPC，不因更新清除人工暂停。健康验证成功后，才由原计划决定何时重新允许新开。

只允许在旧版本可安全读取当前事实和配置时回退代码。新版本产生任何新事实后不得用升级前备份覆盖当前账本。不可逆迁移失败进入复核，不自动降级硬开库。

## 11. 存储、备份与系统维护

保留现有单 writer、提交后派发、WAL 和在线 SQLite 版本要求。[C05] 备份用 SQLite 支持的一致性快照接口，或确认所有连接已正常关闭后的完整备份；运行中禁止只复制主 .db、手删 WAL、清空 UNKNOWN 或原地降级 schema。[R14][R15]

备份结果应记录范围、时间、交易事实水位、schema、版本摘要、校验和与恢复演练结果。凭据单独遵守 Windows 受保护存储策略，不能随普通诊断包明文导出。

备份和日志归档限速、短批次，不在交易 owner 中执行大文件上传、全库检查或长压缩。磁盘不足时先清理允许删除的旧诊断/暂存文件，永不自动删除仍有责任的事实库；事实提交失败保持原故障处理，不能继续无账本下单。

Windows 更新重启、杀毒扫描、系统维护和备份安排到明确维护窗口；不长期关闭安全更新，也不声称应用可以永久否决管理员强制重启。专用机检查电源、网络设备和供电保障；笔记本电池能支撑电脑不代表路由器也有电。

## 12. 告警、界面与可观测性

### 12.1 工作台必须显示实际结果

全天候设置区显示期望状态与观察状态：宿主是否注册/运行、运行账户是否验证、当前执行器及 SHA、自动计划 revision、人工暂停来源、当前/下一合约窗口、日历覆盖、电源模式及保护请求、最近 owner 推进、更新阶段和延后原因。

“后台进程存在”“账户已连接”“行情新鲜”“允许新开”“已有持仓保护已恢复”分别显示。没有 owner 或断线时不能因为某个旧快照存在就显示全部正常。关闭 UI 之后，通知仍必须可由后台发送。

### 12.2 日志合同

沿用既有订单/决定身份，新增长期运行事件：BOOT、PLAN_REVIEWED、START_DUE、START_DEFERRED、MANUAL_PAUSE、RESUME、RECONCILIATION、POWER_CHANGED、POWER_PROTECTION、UPDATE_STAGE、HOST_EXIT、RECOVERY_RESULT。

记录 run_id、owner_boot_id、deployment_id、engine、commit/build hash、plan revision、配置/日历哈希、交易日/会话、命令 ID、阶段、原因、UTC 与单调经过时间。账户仅使用适当受控标识；不记录密码、token、完整凭据或任意异常原文。

重复网络告警聚合为首次、最近、次数和解除事件；高优先级归属/存储/失去保护告警不能被低电量提示淹没。通知失败不阻塞 owner，记录投递状态；断网或整机掉电时本机无法保证发出远程通知，需要外部心跳接收方才能发现整机失联，不能只靠本机承诺。

### 12.3 性能与健康指标

至少测量 owner 最大调度间隙、SDK 驱动间隔、恢复耗时、准备窗口命中、IPC 响应、事实提交延迟、心跳迟到、CPU/内存/句柄、磁盘/WAL 增长和通知丢失。基线与改造后同样负载比较；不以设置纳秒字段推导毫秒响应保证。
