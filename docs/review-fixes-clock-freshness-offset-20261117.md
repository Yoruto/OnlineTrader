## 2. 原因分析与最小反例

### 2.1 CR-01：报价事件时间被用于计算业务经过时间

**源码链路。** `DsvSdkAdapter.step()` 本来取得了独立的 `now, mono = self.clock()`，但随后计算 `market_time = max(self.quote_times.values(), default=None)`，并把它传入 `_frame()` 作为帧时间。`runner._evaluate()` 在 `market_clock` 路径又把每个合约的 `wall_time` 覆盖为最后一笔 tick 的 `native_time`。[S01][S02]

```python
# 当前实现的关键语句，非建议代码
symbol_frame = frame | {'wall_time': market['ticks'][-1]['native_time']}
elapsed = now - float(position['submitted_at'])
```

`_maintain_position()` 的确认超时和被动等待仍按这个时间计算。`controller._desired()` 的非 ACTIVE 价格上下文失效也继续使用 `wall_time - context_at > 90`。因此，即使 owner 继续轮询，报价时间没有前进，这些业务时间差仍可能没有变化。[S03][S04]

**最小反例。** 构造同一个盘段内的两个评估帧：第一帧创建零成交开仓目标，报价时间为 09:40:00；第二帧单调时间已前进 61 秒，但报价仍为 09:40:00。将确认超时在夹具中显式设为 30 秒，且第二帧之前没有其他评估。第二帧的报价时间差仍为零，不能进入确认超时分支。这是测试配置，不是修改生产默认值。

**为何现有断流保护不能兜底。** `_stale_position()` 对 `owned == 0` 直接返回 `False`；未成交订单恰好可能没有已确认持仓。不能把“有持仓时的行情断流退出”当成“所有未成交订单的超时维护”。[S03]

**影响条件。** 连接仍完整、报价对象仍可读取，但价格时间戳停止推进；未成交目标或限价上下文仍有效。此时可能不停止开仓等待、不进入后续价格模式。并非所有手工 STOP／CANCEL 路径都因此失效，不能扩大结论。

**建议。** 业务计时从原业务起算事件绑定单调起点；保留原比较符、条件优先级及部分成交语义。报价只提供行情发生时间，不再提供“等了多久”。细化合同见第 3、4 节。

### 2.2 CR-02：收盘的两个时间输入退化为同一个旧时间

**源码链路。** `_market()` 使用传入的行情聚合时间查询“当前盘段”。`_scheduled_close()` 检查 `wall` 或 `native` 是否进入收盘窗口；但上游已把 `wall_time` 换成该合约的原生报价时间，二者可能完全相同。收盘刷新也用这个 `wall` 计算每 3 秒检查和阶梯经过时间。[S01][S02][S03]

**反例 A：未触发。** 夹具设收盘为 15:00:00，提前窗口为 30 秒。最后报价为 14:59:29，之后不再更新。实际当前时间达到 14:59:31 时，仍用 14:59:29 判定，会继续认为距离收盘还有 31 秒。

**反例 B：已触发但不升级。** 已经在 14:59:35 首次触发收盘处理；此后独立时钟前进 10 秒，报价时间不变。`close_refresh` 看到的经过时间仍为零，原应进行的阶梯检查可能停住。

另一个缺口是 `_maintain_position()` 只有在 `tick is not None`、已有持仓且在盘段中时才调用 `_scheduled_close()`。仅修正时间来源仍无法覆盖完全没有可用 tick 的情况。[S03]

**建议。** 分离“日历退出责任登记”“阶梯状态推进”和“按有效报价规划订单”。前两项不以新行情为前提；第三项继续要求当前执行条件成立。没有合法报价时登记并保留退出责任，不编造报价、不声称已经平仓。

保留 DSV 正常路径已有的双时间触发语义，不悄悄删除报价辅助触发；也不能让异常未来报价或休市前旧报价取得新的发单权限。当前会话、报价所属会话、实际授权必须分别核对。

### 2.3 CR-03：保护退出的 5 秒核对窗口随行情冻结

**源码链路。** `_synchronize_protection_exit()` 以 `frame['wall_time'] - close_request_at` 计算等待，要求 `elapsed >= 5`，同时满足柜台空仓、无外部订单、自有持仓归零及全部子单已终态，才移除 `close_request_at`。`controller.settle()` 在该字段仍存在时不完成收尾。[S03][S04]

**最小反例。** 退出请求已产生，随后柜台回报证明空仓、子单数量一致且终态；本地单调时间经过 60 秒，报价时间仍与退出请求时相同。原时间差仍为零，无法进入 `PROTECTION_EXIT_SYNCHRONIZED`。

**建议。** 5 秒等待使用请求对应的单调起点；账户和订单事实照常驱动同步，不等待行情刷新。

**特别防回归。** 当前实现还保留原版允许的“再次提出同一零目标并更新请求时刻”分支。不能把字段替换成单调时间后，在每个新 timer 唤醒时重新设置起点，否则会制造另一种永久等待。实施前必须固定原业务重提条件：新增的 timer-only 检查不是新保护请求；重复投递不是新请求；真正满足 DSV 原控制流的业务重提仍须按证据保留。不能反过来擅自改成“只有新报价才允许重提”，也不能删除全部重提语义。

### 2.4 CR-04：没有 tick 时，撤单维护与定价一起被跳过

`runner._evaluate()` 在盘段内遇到 `tick is None` 时仅调用 `settle()`；`controller.plan()` 自身也在没有 tick 时直接返回。因此，即使修好计时并把 `entry_stopped` 设为真，仍可能没有形成针对已知自有开仓残单的撤单效果。[S02][S04]

**根因。** 目前“需要行情才能定价的新报单”和“不依赖价格的事实维护／目标缩减撤单”耦合在同一入口，价格缺失挡住了后者。

**建议。** 将维护规划与价格规划分开。只要身份、归属、同步和既有操作权限充分，目标缩减或明确停止对应的取消可以独立规划；没有新报价时禁止的是需要价格证明的新发单／改价，不是全部生命周期维护。

该修复不得绕过取消身份、终态冲突、日切和 UNKNOWN 责任限制。完全断线时可以保留维护意图，但不宣称已成功撤单；连接事实恢复后由原 owner 继续核对和派发。

### 2.5 CR-05：用报价证明自己的年龄，首次旧快照得到零

**源码链路。** 上游帧时间来自报价最大值，下游年龄为观察静默与报价之间的时间差的较大值：[S01][S02]

```python
quote_age = max(
    silence_ms / 1000,
    (_utc(frame['wall_time']) - native_time).total_seconds(),
)
```

首次观察某个报价时，`_observe_market()` 会创建／更新锚点。若只有一个合约，或所有合约返回同一时间的旧快照，帧时间和源时间相同，静默计时也刚刚开始。

**最小反例。** 独立当前时间为 10:10:00，首次收到同一盘段内 10:00:00 的快照。当前算法的两项均可为 0，最终年龄为 0，而不是独立当前时间减源时间得到的 600 秒。重连重新建立会话锚点时也需覆盖这个情形。

**影响边界。** 这证明当前年龄过滤可能被旧快照绕过，不直接证明已发出订单。实际开仓还需满足完整账户事实、授权、行情字段、风险及策略条件。`max_quote_age_seconds > 0` 时，此问题尤其会使用户启用的年龄上限失去预期作用。

**建议。** 分别存储源年龄、观察静默和时间质量；首次观察只初始化静默时间，不能把源年龄标成零。不要把“刚收到”当成“内容是新的”，也不要用另一个合约的时间证明本合约新鲜。

**兼容约束。** `max_quote_age_seconds = 0` 关闭普通策略年龄过滤的语义必须保留。若希望即使该参数为 0，也新增强制的启动／重连陈旧快照拒开规则，应明确登记为异常工程差异并取得业务确认，不能借本次修复偷偷增加固定 5 秒或 15 秒的全局门禁。第 5 节给出实施边界。

### 2.6 CR-06：实时偏移取数仍假设行情不可能领先本机

`read_offset_inputs()` 默认读取 `datetime.now(timezone.utc)`，使用 `0 <= (instant - source).total_seconds() <= 15` 过滤报价。小幅负年龄会静默 `continue`，最后可能只给出“完整日线或当前振幅未同步”的泛化错误。[S05]

**最小反例。** 在同一合法盘段内，源报价持续更新并始终领先本机 800 毫秒，则每轮差值为负，持续不能进入振幅集合。若只是一笔固定快照领先 800 毫秒，之后本机时间追上可能通过，不能声称所有轻微慢钟都会必然耗尽预算。

仓库中的上午复测报告记载过慢钟与领先报价过滤现象，但该报告使用更早基线，且不是本次实时偏移功能的验收记录，只能说明该环境条件具有实际背景。[S08]

**建议。** 共用有符号年龄及时间质量解释，保留偏移用途自己的 15 秒上界；区分报价领先、报价陈旧、日线未就绪、会话不匹配和无法确认时间等原因。禁止用 `abs(age)`、篡改源时间或一律把负数裁为 0 的方式“修复”。

## 3. 总体修复原则

### 3.1 三种时间用途，不建设三个授时系统

| 用途 | 建议来源 | 不允许的替代 |
| --- | --- | --- |
| 当前时刻、日历窗口、授权复核 | 独立采样的 aware UTC；系统授时负责调整，应用只读监测连续性和健康 | 最新 tick、跨合约最大时间、被钳制成只增不减的假 UTC |
| 等待、间隔、超时、周期检查 | 同一可比较时钟域内的单调时间差 | 报价差值、收到 tick 的次数、timer 回调次数 |
| 行情发生时间、原生分钟及源身份 | SDK 原始时间字符串与规范化源时间 | 接收时间、当前系统时间、为了过检查而改写的时间 |

不要求每个 tick 发起 NTP 查询。只读参考暂时不可达不等于已经证明本机时间异常，也不能单凭一次诊断失败停止已有保护职责。明确发现跳变、唤醒或时间冲突时，按已有方案进入有原因、有恢复条件的核对流程。

### 3.2 必须保留的交易不变量

同一账户仍只有一个交易 owner；timer 只要求重新评估，不持有发单端口。事实、状态和必要效果准备必须先经原事务提交，再由原 owner 派发。取消请求不等于取消成功；超时不等于柜台未受理；UNKNOWN 订单继续占用数量，等待核对。持仓退出仍共享一个剩余目标，不增加独立 timer 平仓发送者。[S06]

正常场景继续保持 DSV 信号、分钟消费、偏移公式、风控、部分成交和名义损益语义。异常场景的改进单独登记为工程差异，不能直接写成“原版也是这样”。

### 3.3 不采用的捷径

不全量替换为 `datetime.now()`；它无法独自解决间隔计量、无报价维护和时间跳变问题。不继续用行情最大值提供全账户时间。不引入第二个线程直接撤单、平仓或写账本。不把过期行情直接带入追价，不因为 timer 到期自动放宽价格与归属校验。

也不把定时器数量、纳秒字段或循环频率当成硬实时保证。实际调度迟到需要单独测量和记录。

## 4. 逐项修复设计

### 4.1 建立显式、可注入的时间合同

沿用已有时钟方案的 `ClockSample`／`OT_TIME/2` 设计意图，实施时先检查 `scheduling/clock.py`、`scheduling/reference.py` 中现有类和旧入口依赖，再决定扩展还是新增内聚模块，不能直接覆盖旧 API。

建议逻辑字段如下，**均为拟实施接口，不表示当前已经存在**：

```text
time_semantics_version
clock_epoch
sequence / sampled_mono_ns / sampled_utc / sample_span_ns
decision_utc / authorization_time
source_time_raw / source_time_utc / source_epoch
quote_identity / last_distinct_quote_mono_ns
source_age_raw_ns / silence_ns / age_quality
```

同轮使用一致采样；派发前继续按原边界检查授权与有效输入。JSON 大整数沿用精确字符串约定。现有 `monotonic_ms` 不能直接写入 ns 值；需要明确换算和版本区分。

新在线帧不再设置隐含“报价就是当前时间”的 `market_clock=True` 语义。旧帧由显式兼容解码处理，旧 ROUND 和 checkpoint 不原地改写。`dsv_core` 只能接收时间事实或已计算的经过量，不能主动读取系统时钟。[S06]

### 4.2 计时起点、比较符与重置规则

| 业务 | 保留的当前条件 | 单调计时迁移要求 |
| --- | --- | --- |
| 零成交入场确认 | `elapsed > entry_confirm_timeout`，且未停止、尚无成交 | 绑定原 `submitted_at` 对应的目标创建事件；不是首次柜台回报；部分成交后不扩大该分支 |
| PASSIVE 等待 | `elapsed >= passive_wait_seconds`，且尚无成交 | 使用原 pending 起点；转入 CAP 的阶段更新同事务完成 |
| 价格上下文 | 当前替代链为非 ACTIVE 且 `elapsed > 90` | 绑定原 `context_at` 的创建／合法重置事件；价格算法不变 |
| 保护退出同步 | `elapsed >= 5` 加空仓、归属和子单终态证明 | 绑定实际保护请求版本；重提条件先以 DSV 对照固定 |
| 收盘刷新 | 首次进入，或距上次刷新 `>= 3` 秒 | 不随重复报价重置；迟到只对当前状态检查一次 |
| 收盘阶梯 | 原公式按首次收盘处理后的经过时间选择模式 | 保留公式和起点，不偷偷换成按收盘绝对剩余时间的另一算法 |
| 行情静默 | 原字符串身份变化与单调静默计量 | 重读缓存、账户回报和无关合约更新均不重置 |
| 冷却等其他相对等待 | 按各自原函数及配置核对 | 同一批形成读取清单；不得只修上述几个字段就宣称全部迁移 |

有关源版其他上下文时长的差异，沿用上位方案单独追踪；不能因本文列出当前 90 秒分支就声称全部追价模式已经与 DSV 对齐。

计时记录至少绑定账户作用域、合约、目标／持仓 ID、业务类型、generation、起算事件、clock epoch、duration 和比较符。旧 generation 的唤醒不得操作新目标。同一进程重连不应自动把未完成业务的计时归零；行情 epoch 与 clock epoch 分开。

### 4.3 owner 必须在没有行情更新时继续维护

保留单 owner 循环，只调整其唤醒与评估职责。建议控制流如下；这是设计伪代码，不是可直接替换的实现：

```text
有界驱动 SDK，收集本轮已取得的账户／订单／成交事实
→ 采样独立时钟并识别异常
→ 按原顺序核对和应用 native 事实
→ 对仍有效的目标／阶段检查到期条件
→ 规划无需价格的维护与取消
→ 在行情及执行条件允许时规划价格相关动作／原策略信号
→ 事务提交后，由同一 owner 派发已提交效果
```

即使 `wait_update()` 没有新行情，仍处理到期检查；账户回报先于对旧状态的超时判断。例如同轮先收到 3 手成交，就不能仍把 5 手目标按“零成交超时”处理。[S06]

业务剩余时间用单调差计算，再换算成 SDK 接受的等待期限；不能把单调绝对值直接传入 Unix deadline。初始轮询上限可沿用基线 0.5 秒，并向更近 deadline 缩短。该数值是实现起点，不是延迟服务等级保证。等于严格 `>` 边界时要避免零等待忙循环，但不能把比较符改成 `>=`。

周期迟到合并为一次最新检查，不补发全部历史撤改单。SDK 驱动、事务耗时和诊断 I/O 的迟到分别记录；不能靠第二个并发 SDK 调用线程强行补救卡顿。

### 4.4 维护规划与价格规划分离

建议在 `ExplicitOrderController` 内形成两个清晰阶段，名称可在实现 PR 内确定：

| 阶段 | 可执行的工作 | 仍需的证明 |
| --- | --- | --- |
| 生命周期维护 | 应用终态、结束已证明完成的目标、为明确目标缩减／停止生成自有订单取消意图 | 账户和订单身份、同步、归属、当前冲突处理和操作权限 |
| 价格相关规划 | 新开仓、平仓报单、按最新合法价格决定是否撤换 | 上述证明，加可用行情、合法价格、数量与平今／平昨路由、当前时段和授权 |

移除的应是“无价格就跳过所有维护”的耦合，不是移除风控。已有可继续工作的退出挂单不能仅因为没有行情而盲目撤掉；否则可能把保护能力降低。

对未知发单结果不生成重复子单；对尚未确认的取消不释放占用；对明确未发送的请求继续使用原分类与重试合同。不能把所有错误都降级为“肯定没发”。

### 4.5 收盘责任、价格和统计分别保存

独立查询当前盘段与报价所属盘段。当前时间进入有效清仓窗口时，以稳定身份登记退出责任；身份包含账户作用域、合约、柜台交易日、盘段和业务版本，防止跳钟或重复 timer 重复登记。

无报价时可以记录“应退出、等待合法执行条件”，但不得合成价格，也不能用旧报价冒充当前名义损益参考。已有可证明的订单和成交继续核对；恢复合法报价后按当前剩余目标和退出阶段规划，不从初始阶段重新开始、不重放全部历史阶梯。

若调度暂停跨过整个窗口，应记录错过日历事件并保留待处理责任；休市后不补发过时委托，也不补开历史入场信号。下一合法执行机会必须重新核对账户、交易日、平仓路由和现有挂单。

午休盘段与最终清仓终点分别使用现有日历字段，不把每个盘段结束都改为强平。没有独立柜台日证明时，不因本机午夜或某合约异常时间自行推进账户交易日。

## 5. 行情年龄、启动／重连与偏移计算

### 5.1 年龄不能再自证

建议同时保留以下三项，不压缩成一个来源不明的“延迟”：

```text
source_age = independent_decision_utc - source_time_utc    # 有符号
silence = current_mono - last_distinct_quote_mono          # 观察后静默
quality = 对时钟连续性、源身份和会话有效性的解释
```

首次观察旧数据可以有 `silence = 0`，但 `source_age` 仍必须从独立当前时间计算。拿不到可信源年龄时标记 UNKNOWN／原因，不填写 0。显示层也不把负年龄显示为“零延迟、健康”。

有符号原始年龄保留诊断精度；真正用于 DSV 普通年龄规则的比较口径，继续遵循已固定的数值精度／截秒行为。正数配置执行原上限及边界；0 仅关闭该项策略过滤，不取消源身份、价格或会话约束。

### 5.2 不以健康监测状态暗改交易授权

启动／重连首先核对账户事实、报价身份与盘段、原有授权，再按当前用途解释行情年龄。不同合约分别记录质量，不因一个异常合约的时间推进其他合约的日历。

没有新鲜 NTP 诊断样本，不自动等于源年龄不可计算或全局禁止交易；已确认大幅跳钟、源时间矛盾等才进入明确的异常状态。不能把健康监测线程的布尔值直接变成隐藏交易开关。

对于正数年龄上限下明确超龄的首次快照，应按既有年龄规则拒绝开仓。对于年龄限制为 0、时间证据不足或额外强制首次快照门禁的情形，必须在实施 PR 的差异表中明确政策和理由，完成业务确认后再启用；本文不暗示新增政策已经获得上线授权。

已有风险责任不因拒绝新开仓而消失。时钟异常期间继续接收订单和成交、维护已知目标；可证明的自有取消按原权限执行。需要新价格的退出动作仍核对价格质量，不用异常时间为其赋予许可。

### 5.3 负年龄处理必须有用途和证据边界

不采用统一 `abs(age) <= N`、统一固定 ±1 秒或无限接受未来报价。具体解释至少区分轻微领先且无其他冲突、明显异常未来时间、时钟不连续、源倒退和会话不符。

诊断阈值、普通策略年龄上限、偏移计算取数上限不是同一个参数。轻微领先的可接受条件和容差来源应在实施的参数／差异清单中固定，提供边界夹具；没有部署证据前不声称某个数值适合全部环境。

### 5.4 实时偏移计算的改动边界

`read_offset_inputs()` 接收可注入时钟／年龄解释器，避免默认路径与测试路径分别维护不同判断。日历查询使用独立当前时间，仍要求所有选中合约处于共同合法会话，源报价属于正确盘段，日线严格完成并匹配截止交易日。

建议错误结果按合约附带结构化原因，例如 `QUOTE_TIME_AHEAD`、`QUOTE_TOO_OLD`、`CLOCK_UNCERTAIN`、`SESSION_MISMATCH`、`DAILY_NOT_READY`。这些名称是拟新增诊断码；实现时与现有错误体系统一，不随意泄露 SDK 异常全文。

只有行情时间解释问题时，不应最终只显示日线未同步。预算耗尽时保留最后一个可解释原因及必要原始差值；不得因改善报错而无限延长读取。

保持只读行情会话、关闭清理、账号选择复核和参数预览边界。不在失败时沿用上次振幅伪装为本次结果，不使用未完成日线补齐，不自动发布参数或激活策略。偏移公式、15 秒用途上界和正常计算结果不借本次修复改变。

## 6. 持久化、重启与异常恢复

新增计时身份、版本、起算事件和阶段更新，应与对应状态／效果准备在原事务中提交。周期扫描本身不必每次落一条庞大事件；仅持久化改变责任的事件，诊断采用有界聚合。

同一进程连接重建可以保留业务单调起点，但需要确认 clock epoch 未变。进程重启、换机或不同可比较域之间，不直接相减持久化的单调数值。恢复先处理 native 事实，再恢复计时和目标。

旧版 `submitted_at/context_at/close_request_at` 可能已经是报价时间，不能批量当成真实创建 UTC 来迁移。能从原事件证明起点的才恢复剩余时间；不能证明的进入明确的 `TIMER_RECOVERY_UNCERTAIN` 路径，保留责任、不假造到期、不重置为完整新等待周期、不盲重报。

若新版已有可核对的起算 UTC 和完整连续性证据，可据此重建剩余时长，并绑定新的 clock epoch；已到期责任核对后处理一次。无法证明时不得拿“程序重启了”替代业务决定。

迁移必须定义最低读取／写入版本和旧 writer 拒绝规则；保留旧事件、订单 ID、成交身份、价格数量和归属。用冷备份与合成账本验收，不对运行中数据库试验。回滚时不能直接用旧库覆盖可能含新增成交的账本，也不能让旧程序忽略新字段继续写入。

休眠／唤醒、墙钟前跳后退、长时间线程停顿均要先核对当前事实与时段，再处理一次当前有效责任。Linux 离线通过不替代 Windows 目标环境验收；是否限制自动休眠属于运行配置，不代替恢复能力。

### 7.2 分批建议

**批次 A：固定反例与兼容合同。** 新增确定性夹具，列清所有时间读取点、计时起算事件、比较符和业务优先级；记录旧基线触发错误的条件。测试应描述正确行为，不能把当前错误输出当永久期望。

**批次 B：候选链最小完整修复。** 同时完成独立当前时间、业务单调计时、无报价维护和收盘责任登记。不得只合入 `wall_time` 替换就作为可发布修复。先用离线 API 替身跑完整 adapter → session → controller → journal 链，验证发单／取消效果和重启恢复。

**批次 C：源年龄与偏移取数。** 修正首次旧快照年龄，处理重连、跨合约隔离、负年龄和用途专属错误。普通年龄开关为 0 时的额外策略必须先完成差异确认。正数上限的数学错误修复不应被这项讨论无限阻塞。

**批次 D：其他入口与恢复覆盖。** 分别验证旧桌面链、候选链、只读偏移取数；完成时间 schema 迁移、断线、跳钟、暂停和旧 writer 拒绝测试。没有覆盖到的入口明确保留 NOT_RUN／未放行。

**批次 E：目标环境和交易闭环验收。** 在另行明确授权下进行 Windows、冻结 DSV 同输入及受限模拟账户验收。覆盖自然入场、发单、回报、部分成交、撤单、保护退出和重启核对，不用零委托／零成交的行情对照替代。

每批提交应注明候选完整 SHA、实际入口和剩余未关闭问题；不重新启用 CI/CD。文档提交本身不改变上述问题的未完成状态。

| T13 | 当前 10:10，首次快照 10:00，同一盘段，正数年龄上限 | 源年龄为独立差值，不是零；按配置拒绝陈旧开仓输入 |
